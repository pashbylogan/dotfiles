Decision Log

Decisions & rationale

Every load-bearing choice, with the reason it was made. Each has a stable ID (see Trace); the D-ID tags below are grep targets.

Core architecture

Decision Choice Why
D-ENGINE Convergence engine Lightweight shell + Omarchy CLI + stow. No Ansible, no dot-apply/check/update/cleanup engine. Omarchy already does install/seed/migrate/update. A convergence framework would re-implement that and accrue code that must survive upstream churn.
D-SCRIPTS-MINIMAL Scripts One convergence script: install. User commands may be stowed under bin/.local/bin, but package updates and cleanup remain explicit operator actions. Owner chose pure-minimal. Updates run via make update / omarchy update -y; package cleanup uses packages.remove.txt plus read-only audits such as pkg-residue, not an automatic cleanup engine.
D-DELTA-STORAGE Delta storage Own thin fragments + single managed integration block. Never symlink Omarchy-owned files. (Full detail: Architecture.) Omarchy cp-resets write through symlinks (F-REFRESH-WRITETHROUGH); owning whole files freezes them and breaks on the coming Lua move (F-LUA).

Repo hygiene & CI

Decision Choice Why
D-CI Makefile = ops interface A root Makefile is the single source of truth for repo operations. GitHub Actions (.github/workflows/ci.yml) invokes the same targets, so make ci == CI. Targets:
  • make ci — gates: shellcheck + shfmt (-i 2 -ci) on the shell set, pinned prettier on docs HTML/JSON, an empty-object smoke-check of every waybar/*.jq filter (so jq syntax/behavior bugs surface here rather than at ./install time), and .github/scripts/check_docs.py for docs integrity. make fmt auto-fixes.
  • make update — the frequent, low-risk channel: omarchy update -y (pacman + AUR + omarchy migrations), then the package-like self-managed tools (uv self update, then mise upgrade + mise prune), then make verify. Every step is warn-on-failure so a non-zero exit (reboot decline/request, package-manager interruption, etc.) stays visible. mise upgrade honors the specs in ~/.config/mise/config.toml — latest resolves to the newest stable release (prereleases and nightlies are excluded unless a spec explicitly asks for one) and exact pins are left untouched — and omits --bump so the config is never rewritten; mise prune then reclaims superseded or orphaned versions.
  • make update-firmware — firmware only: omarchy update firmware (fwupd). It is the lone opt-in channel because firmware alone — unlike packages or the self-managed tools folded into make update — has device-specific prompts and reboot/power-cycle outcomes.
  • make verify — read-only live health check (.github/scripts/verify.sh): hyprctl configerrors, all seven managed blocks present (bashrc, hypr, keymaps, tmux, waybar style.css, alacritty, starship-venv), stow links resolve into the repo (including the uwsm/env.d SSH-agent fragment and dangling detection), dev-env tools on PATH and not pacman-owned, XDG state, and the default-tracking override comparison (border_size = 2 vs omarchy's looknfeel.conf default — see D-LOOKNFEEL).
  • make pkg-residue PACKAGE=<name> — wrapper around the stowed pkg-residue command for read-only package-leftover audits.
Tooling is Omarchy-native and version-pinned. 		One interface for humans and agents; CI calling the Makefile means the two can't drift. The docs checker turns the traceability discipline (registry ↔ anchors ↔ [ID] code tokens, links, appears_in) into an enforced invariant rather than a convention. The Makefile is dev/ops tooling; the lone runtime script is still install (D-SCRIPTS-MINIMAL).
D-DEV-ENV dev-env reconcile uv and go are owned by Omarchy's omarchy install dev-env <kind> path, not by pacman/AUR or hand-rolled installers. ./install's ensure_dev_env_tool helper actively reconciles: if pacman owns the tool, omarchy pkg drop it (graceful on dep-conflict refusal); if not on PATH, install via omarchy install dev-env. No path pinning — omarchy lands each tool wherever the underlying installer defaults today (Astral's ~/.local/bin/uv; mise's ~/.local/share/mise/shims/go) and command -v finds it. The user's rule: if a tool is installed in a way the repo doesn't declare, it should get replaced. Reconciling on ./install enforces that for the main drift vector (pacman) while staying robust to upstream path changes. Latest-at-bootstrap caveat: omarchy install dev-env pulls latest at the time it runs (mise @latest, Astral installer), so a fresh bootstrap on different days may yield different versions; make update is the deliberate bumper for self-managed tool updates (uv self update + mise upgrade/prune, stable-only).
D-PKG-REMOVE Baseline package/app curation Package and launcher curation mechanisms that converge the post–Remove-Preinstalled baseline.
  • packages.txt / packages.aur.txt — additive package restores and extras, processed through omarchy pkg add / omarchy pkg aur add. This includes restoring selected Omarchy defaults after Remove Preinstalled, such as pacman-managed opencode. App channel choices follow the Omarchy-native audit in F-APP-CHANNELS: obsidian stays in the official repo, spotify stays on Omarchy's AUR path, and slack-desktop is an intentional local AUR choice because Omarchy has no Slack package, webapp, binding, or migration. claude-code is force-installed from the AUR via yay -S --needed aur/claude-code because Omarchy publishes a stale same-name package that hides it from generic yay -Sua.
  • packages.remove.txt — symmetric subtractive partner to packages.txt / packages.aur.txt, processed via omarchy pkg drop after both add steps so a name in both files resolves to "removed". Wrapped in warn-and-continue because pacman -Rns can refuse on reverse-dep conflicts. Empty list → no-op; already-absent names → no-op at the omarchy CLI layer. Scope: pacman-tracked only (official-repo + AUR). Web apps are not pacman packages; remove those with omarchy webapp remove.
  • elephant/.config/elephant/websearch.toml — stowed override of elephant's compiled-in default web-search entry (Google). Walker's app picker queries elephant; the TOML override is the elephant-generated, elephant-doc'd way to set custom engines. Defaults to DuckDuckGo here.
  • Stale-launcher cleanup in install — explicit rm -f for known orphan ~/.local/share/applications/*.desktop files whose underlying package is gone but the user-dir launcher remained (pacman -Rns only removes files the package installed, not user-state files copied there later).
  • bin/.local/bin/pkg-residue — read-only audit for package leftovers after removal. It derives search terms from the package name and any known pacman/cache file list, uses rg --files as the fast path for file matches, uses find -type d for directory matches, filters paths owned by pacman, and reports likely residual user state, system state, and package cache entries without deleting anything.
The repo's overlay surface was previously additive-only for packages and silent on user-state under ~/.local/share/applications/ and ~/.config/elephant/. The "Deeper package cleanup" backlog wanted a way to express "drop this omarchy default" without depending on the one-shot Remove Preinstalled menu (per D-BASELINE, that menu action is the documented manual prerequisite, not a substitute for ongoing curation). The same package surface can also restore an upstream default when the current durable Omarchy path is still desirable: opencode stays a pacman package, and install uses omarchy refresh config only to seed a missing opencode.json instead of vendoring it here. One token, several mechanisms — because they share the same intent (curate the baseline) but live on different surfaces (pacman db, stowed config, user-state launchers). Audit rule: before adding a name to packages.remove.txt, grep ~/.local/share/omarchy/ for usage — omarchy wires some "builtins" into keybindings or shell init (e.g. zoxide → cd alias, fzf → keybindings, btop → SUPER+CTRL+T). Removing one of those silently breaks omarchy commands, so clean up the matching wiring in our overlay in the same change (e.g. an unbind in hypr.conf for a keybound tool — which is exactly why btop and eza are not dropped: btop is keybound and eza backs the ls alias).
D-WEBAPP Reproduce curated webapp launchers install re-creates the omarchy webapp launchers we rely on by calling omarchy's own omarchy webapp install with the exact arguments from omarchy's webapps.sh — currently just Zoom (app.zoom.us/wc/home + omarchy-webapp-handler-zoom + zoommtg:///zoomus:// scheme handlers). Idempotent: the installer rewrites the .desktop on every run; we re-copy omarchy's own Zoom.png into ~/.local/share/applications/icons/ (omarchy's icons.sh seeds it at first install) and refresh the desktop database so the zoommtg:// handler registers. Removal stays on omarchy's surface too: omarchy webapp remove Zoom. omarchy installs its curated webapps only at first install — webapps.sh doesn't re-run on omarchy update, and Remove Preinstalled / a fresh machine drop them. Calling omarchy's installer rather than hand-writing a .desktop keeps the launcher byte-identical to upstream and inherits the protocol handler. Zoom is the webapp, not the AUR native client: on Wayland the native client's screen-share is unreliable (black screen / crash on re-share), while the Chromium PWA shares screen through the browser's portal — the mirror image of discord, where the native client wins for global push-to-talk + desktop-audio share. Slack is not reproduced as an Omarchy webapp: unlike Zoom, Omarchy does not ship one, and Slack's Linux huddle support is documented for the desktop app and Google Chrome. Keep native slack-desktop as the daily client; fall back to Chrome only if huddles/screen sharing regress.
D-BROWSER-DEFAULT Default browser Stable Brave Origin is the converged default browser. Until a released Omarchy version maps its Brave Origin install/default commands to stable, install uses Omarchy's package and theming surfaces directly: omarchy pkg aur add brave-origin-bin, Omarchy's shared Brave policy directory, ~/.config/brave-origin-flags.conf, and omarchy-theme-set-browser. It then sets XDG's browser and web MIME defaults to brave-origin.desktop and drops the old brave-origin-beta-bin package. Omarchy's current browser installer/default wrappers still map brave-origin to brave-origin-beta-bin and brave-origin-beta.desktop. Brave now documents brave-origin-bin as the release Arch package, and upstream Omarchy PR #6021 tracks the same migration. This repo keeps the transition as close to native as possible by reusing Omarchy's package manager, Chromium extension flag, Brave policy theming, and theme-set hook surface. Once a released Omarchy version maps brave-origin to stable, remove the compatibility code and return to omarchy install browser brave-origin / omarchy default browser brave-origin.

Shell

Decision Choice Why
D-SHELL-BASH Login shell bash (Omarchy default). No chsh to zsh. Omarchy's boot/session/helpers assume bash; chsh→zsh is a documented footgun (F-SHELL-RESEARCH). Omarchy's bash already wires starship/zoxide/fzf/mise, so zsh's marginal gain is small.
D-SHELL-SEAM Aliases/functions Ported into ~/.config/dotfiles/shell.sh, sourced via the ~/.bashrc managed block (at EOF, so ours win). ~/.bashrc is owner-owned and "not overwritten on updates" (F-BASH-CHAIN). Aliases Omarchy already defines (t, g, gcm, gcam, n, cd/zoxide, ls/eza) are dropped in favor of Omarchy's.
D-SECRETS-LOCAL Secrets/host-specific Gitignored shell.local.sh holds personal and device-specific aliases, functions, and keybinds (Vertex project IDs, device serials, the Ctrl-F sessionizer bind, VPN/GCP helpers) — never install-path redirects, since Omarchy installs tools (uv, gcloud, …) natively on PATH. Keep the shared repo generic and secret-free.

Hyprland deltas (i3 "spirit", confirmed item-by-item)

Most i3 customizations were already done or native on Omarchy (key-repeat, touchpad scroll, thin borders, move-ws-to-monitor, volume/brightness/screenshot/lock keys, launcher, wallpaper). Only three were genuine:

Delta Status Notes
D-CAPS-CTRL caps lock → control in (fragment) Moved off Omarchy's seeded input.conf into the owned fragment, sourced last.
D-WORKSPACE-RULES Workspace app-assignments in windowrule = workspace N (terminal→1, Brave Origin→2, Slack+Obsidian→3, IntelliJ→5, Spotify→10). Verify classes via hyprctl clients.
D-SLACK-HUDDLE-FLOAT Float Slack huddle, tile the main window in (fragment) windowrule = float on, match:class slack, match:title Huddle. Every Slack window shares class=slack, so the rule keys on title. float is a static rule, so Hyprland matches it against initialTitle — the huddle window's is Slack - Huddle Preview while the main window's is just Slack, so only the huddle floats. Match the bare word Huddle (no colon — a : breaks Hyprland's RE2 regex). Verify titles via hyprctl clients.
D-SCREENSHOT-FALLBACK Screenshot fallback in (fragment) SUPER+SHIFT+S invokes omarchy-capture-screenshot while the keyboard's physical PRINT key emits no Linux input event. Omarchy's stock PRINT binding stays intact; the fallback uses a live-conflict-checked key and remains easy to remove when firmware/profile behavior is fixed.
D-MOUSE-ACCEL External MX Master mouse accel in (local) Device-specific → gitignored hypr.local.conf.
D-HJKL-DECLINED vim hjkl window focus declined Would require unbinding Omarchy's SUPER+J/SUPER+L. Keep Omarchy's SUPER+arrows.
D-LOOKNFEEL Looknfeel deltas in (fragment) An always-on "compact look" of overlay-sourced-last deltas to omarchy's looknfeel chain: (1) general { gaps_in = 2; gaps_out = 4 } — slim but present gaps (omarchy's defaults are 5/10); (2) general { border_size = 2 } so the window-no-gaps toggle keeps killing gaps without also killing borders — this is the single line in any overlay that re-states an omarchy default value (border_size = 2 in looknfeel.conf) because that downstream toggle would otherwise zero it, so make verify compares the two and fails loudly if omarchy ever moves their default; (3) decoration { rounding = 8 } — every corner rounds at omarchy's documented radius (the commented rounding = 8 hint in its looknfeel.conf template, and the same radius omarchy applies to popups via rounding 8, match:tag pop in default/hypr/apps/system.conf); (4) decoration { blur { size = 8; brightness = 0.72 } } plus windowrule = opacity 0.86 0.78, match:tag terminal so terminals get a mild frosted-glass effect without hard-coding terminal colors or breaking omarchy theme swaps; (5) misc { focus_on_activate = false } so an app's activation request (chat message, browser opening a link, a finished build) only marks the window urgent instead of stealing focus and jumping you to its workspace — omarchy sets this true in default/hypr/looknfeel.conf whereas Hyprland's own default is false, so this inverts an omarchy non-default rather than re-stating a default (no make verify guard needed, unlike border_size). Because the fragment is sourced after both omarchy's defaults and the window-no-gaps toggle in hyprland.conf's source chain, these values win regardless of toggle state — editing ~/.config/hypr/looknfeel.conf wouldn't, since it loads before the toggle. See F-HYPR-SEAM for the full ordering.
D-MONITORS Known external monitor layouts in (fragment) Three monitor = lines in the overlay encode known external displays. The home dock layout is: DP-5 (Acer XV272U) primary at 0x0, DP-4 (Acer XV272U V) secondary at 1920x0, both at native 2560×1440 @ 144 Hz and compositor scale 1.333333 (effective logical 1920×1080 per panel — the secondary's position is in scaled pixels, hence 1920x0 rather than 2560x0; see F-MONITOR-SCALE-PERSIST for why we set scale in the overlay rather than via the Super + / cycle). The work monitor is DP-1 (Dell U2719DC) at 0x0, native 2560×1440 @ 59.95 Hz, compositor scale 1.25; its EDID advertises no higher-refresh native mode, so this rule favors the best-quality native resolution over lower resolution 75 Hz fallbacks. All are matched by full desc: identifier (description string up to but not including the trailing portname, per the Hyprland wiki — see F-MONITOR-RULE-APPLY) so cable-swaps between DP ports don't change the layout. The full serial tail is load-bearing because both Acer descriptions share the Acer Technologies XV272U prefix — a panel swap (same model, new EDID serial) silently falls through to the omarchy wildcard, so update the desc: string when that happens. No hot-plug script: Hyprland re-applies monitor = rules on every monitor connect, which is the same matcher behavior that makes omarchy's seeded fallback monitor=,preferred,auto,auto work; the omarchy-shipped omarchy-hyprland-monitor-watch already covers removal recovery. No workspace = N, monitor:… pins — on a fresh session, Hyprland assigns workspace 1 to the leftmost monitor by position (DP-5 at 0x0), which is what "primary" means here (Hyprland has no xrandr-style primary concept). One nuance: when these rules first land via hyprctl reload on a running session, the existing workspace→monitor bindings are preserved — workspace 1 stays on whichever monitor it was on, and fully migrates only on next fresh login (or move it now with hyprctl dispatch movecurrentworkspacetomonitor DP-5). Install restarts waybar on topology change: install's validation block snapshots hyprctl monitors around the post-stow hyprctl reload (extracting name/position/mode/disabled per output) and, if the snapshot diff is non-empty, invokes omarchy-restart-waybar with the same poll-and-confirm pattern as the waybar-overlay restart. Waybar's per-output bars don't always survive a layout flip; this is the integration step that makes a fresh ./install after a monitor = edit reach a fully-rendered desktop without a manual restart. eDP-1 is deliberately not in the overlay: omarchy's lid-switch handler at default/hypr/bindings/utilities.conf calls omarchy-hyprland-monitor-internal off/on, which writes monitor=eDP-1,disable to ~/.local/state/omarchy/toggles/hypr/internal-monitor-disable.conf. Our overlay loads after the toggles (F-HYPR-SEAM), so an explicit eDP-1 rule here would silently beat the toggle. The wildcard monitor=,preferred,auto,auto already activates eDP-1 at its only supported mode (1920×1200 @ 120 Hz) when the toggle isn't present. Same load-order pattern as D-LOOKNFEEL but inverted: silence to let the downstream toggle win, instead of re-stating to beat it. GDK_SCALE intentionally untouched: omarchy seeds env = GDK_SCALE,2 in monitors.conf (right for the laptop's 13"/2.8K panel). GDK_SCALE is process-global on Wayland — there is no per-monitor GTK scaling without per-app launchers — so dropping it to 1 for the 1440p externals would shrink GTK apps on eDP-1. The compositor scale in our monitor = lines is the in-scope correctness step; the GTK-oversize trade on the externals is acceptable until per-app launchers become worth it. Forward risk: when omarchy ships the Lua hyprland config (F-LUA), these lines become hl.monitor({…}) calls; the design is unaffected.
D-KINESIS-REMAP Kinesis Adv360 SmartSet thumb remap done Profile-1 thumb cluster reworked for Omarchy's SUPER-centric binds: SUPER on both bottom thumb keys ([end]>[lwin], [pgdn]>[rwin]) for either-hand chording; Alt moved to the freed inner-right key ([rwin]>[ralt]); Home→Tab ([home]>[tab]) so SUPER/ALT+Tab are thumb gestures; and Calc→F14 ([pgup]>[f14]) bound by keycode (code:192, since F13+ keysyms map unreliably through xkb) to the clipboard manager. Caps left as-is; Delete stays on the fn layer. Layout backed up at kinesis/layout1.txt.

Waybar deltas

Waybar's config sits in ~/.config/waybar/config.jsonc, an omarchy-seeded file that the live system mutates two different ways (F-WAYBAR-MIGRATIONS). Omarchy's manual recommends direct edits and treats periodic .bak restores as the recovery story; this repo applies D-DELTA-STORAGE to JSON instead: own thin deltas, re-apply them every ./install, restart only on real change.

Decision Choice Why
D-WAYBAR-DELTAS Waybar overlay shape Two coupled overlays: waybar/deltas.jq holds personal config.jsonc deltas as composed jq filters; a managed block in style.css (via the existing upsert_block helper) carries the matching CSS rules. install's apply_jq_deltas applies the jq filters idempotently; the style block is re-anchored at EOF the same way as the bashrc/hyprland/tmux/keymaps blocks. waybar is only restarted when content actually changed (hash-compare around both files), and the restart waits-and-polls pgrep -x waybar to verify the process actually came back. Initial deltas: drop the 1-5 persistent-workspaces pin so workspaces grow on demand (i3-style), add an icon-only memory module on the same 5 s nominal interval as cpu (with used/total/% in tooltip-format on hover), and extend omarchy's #cpu, #battery, ... CSS spacing rule to include #memory so the new module renders with the same margins as its neighbors. Urgent workspaces: omarchy ships no urgent styling, and its #workspaces button { all: initial } reset means a workspace flagged urgent shows nothing — so with focus_on_activate off a window requesting attention would be invisible. The block adds a #workspaces button.urgent label rule that recolors the workspace digit to a muted red #a55555 — the same attention accent the bar already uses for its screen-record/idle/notify-silence indicators — reproducing i3's number-color cue. It targets the label node because omarchy's global * { color: @foreground } paints the digit directly, overriding a button-only color rule. The color is a literal for the same reason as the tray accent below — waybar CSS only receives @foreground/@background, never the theme's per-theme accent. Spacing rationale: omarchy ships an asymmetric right side — #custom-expand-icon has margin-right: 18 px, #bluetooth 17 px, #tray 16 px, #network 13 px, while #cpu/#battery/#pulseaudio share margin: 0 7.5 px and #memory gets no rule at all. We flatten every right-side module to margin: 0 4 px on each side (equidistant ~8 px gaps, snug but not pinched). The override wins via CSS's later-rule-wins ordering — our managed block sits at EOF of style.css, after omarchy's per-module rules. Tray menu hover: the same block also restores the right-click tray (dbusmenu) context-menu hover highlight. omarchy's * { background-color: @background } reset loads at GTK application priority, beating the theme's menuitem:hover by priority rather than specificity — so hovered rows never highlighted. Worse, that reset paints an opaque @background box on every node, including each menuitem's label, so a row-level highlight would only show at the edges with a dark box behind the text. The fix is two same-sheet rules that win by specificity: clear the box on the menuitem content nodes (label/arrow/check/radio → background-color: transparent), then tint the hovered row with alpha(@theme_selected_bg_color, 0.4). The tint — rather than a solid fill with a foreground/background flip — keeps the menu's dark base so the unchanged light text stays readable; the label-color override a solid highlight would need doesn't take in GTK3's menu nodes (the text rendered invisible). @theme_selected_bg_color is GTK's built-in selection accent (always defined), so it gives a distinct hue without hardcoding. omarchy exposes only @foreground/@background to waybar CSS and keeps its per-theme accent (#7aa2f7 for Tokyo Night) in colors.toml, which GTK CSS can't read — matching the accent per-theme would need a separate theme-set hook bridge, out of scope for a tray highlight. Forking the whole file would silently drop every future surgical migration (F-WAYBAR-MIGRATIONS); direct edits would be wiped on the next omarchy-refresh-waybar and only recoverable through a .bak diff. Owning only the deltas survives both mutation patterns: refresh overwrites get re-patched on next install, surgical migrations either pre-date our filter or touch keys our filter doesn't (the memory module uses a merge pattern so future upstream keys survive). Each delta was battery-audited: memory uses the same 5 s nominal interval as cpu — waybar runs per-module timers independently so this isn't strict coalescing, but it's the cheapest practical cadence. A verbose 1 s clock tick was considered and deliberately rejected because it would prevent deep C-states.

Terminal (Alacritty) deltas

Decision Choice Why
D-ALACRITTY-MOUSE Disable right-click paste A managed block in ~/.config/alacritty/alacritty.toml binds Right mouse to action = "None". Alacritty's built-in default is right-click = ExpandSelection and middle-click = PasteSelection (primary selection); omarchy ships no [mouse] config, so the no-op overlays the built-in default and right-click stops doing anything (no paste). Appended at EOF via the same upsert_block helper as the other integration blocks; Alacritty's live_config_reload (default on) picks it up, so install needs no restart step. Shift+Insert paste and OSC52 are untouched. The managed block is the repo's tracked-delta convention, not omarchy's own recommendation — omarchy's manual says to edit ~/.config/alacritty/alacritty.toml directly, and omarchy treats it as user-editable: its updates surgically sed-patch specific lines in place (the Shift/Ctrl+Insert binds, opacity removal, font-set's family rewrite) rather than overwriting the file, and only the manual omarchy refresh config alacritty/alacritty.toml cp-resets it. We use a block anyway because a direct edit isn't reproducible: the repo's job is to re-apply tracked deltas on every ./install, demarcated from omarchy's content, idempotently — the same pattern as the other integration blocks, and omarchy's line-targeted seds leave an EOF block alone. Not stowed because both omarchy's sed -i migrations and the manual refresh write through a symlink, so stowing would let omarchy mutate our tracked copy (F-REFRESH-WRITETHROUGH); owning the whole file would also freeze omarchy's seeded defaults. Owning only the one-line delta (D-DELTA-STORAGE) is the same trade as D-WAYBAR-DELTAS. Alacritty's general.import seam doesn't help: adding our file to that array means editing the owned import line in place (TOML can't merge two import keys via append), which is strictly worse than the appended block.

Prompt (Starship) deltas

Decision Choice Why
D-STARSHIP-VENV Show the active Python venv name in the prompt A [custom.venv] module keyed on $VIRTUAL_ENV prints just the active venv's name (e.g. (.venv)) — and nothing when no venv is active, in any directory. Omarchy seeds a stripped format = "[$directory$git_branch$git_status]($style)$character". install inserts ${custom.venv} before $character (in-place, grep-guarded) and appends the module table as a standard upsert_block managed block that runs basename "$VIRTUAL_ENV" when $VIRTUAL_ENV is set, styled italic yellow. verify.sh greps the ${custom.venv} format reference and check_blocks the module. A $VIRTUAL_ENV-keyed custom module, not starship's native python module. The python module is starship's default venv display, but it only renders inside a detected Python-project directory and bundles via 🐍 <version>; the goal here is just the venv name, shown whenever a venv is active regardless of directory — exactly what a custom module on $VIRTUAL_ENV expresses. Storage is a hybrid in-place delta: the format reference must edit Omarchy's scalar format key — starship has no include and TOML can't merge two formats. D-ALACRITTY-MOUSE sidesteps that wall by appending a separate [[mouse.bindings]] table and D-WAYBAR-DELTAS uses structured jq, but a format reference has no append or merge option, so this is a deliberate text-level sed — the repo's one in-place text edit. The module table, by contrast, is append-only and rides the standard managed block. Not stowed: ~/.config/starship.toml is seeded once (an Omarchy migration cps the default only if omarchy-cmd-missing starship), is never auto-refreshed, and only the manual omarchy refresh config starship.toml rewrites it — its cp -f would write through a stow symlink (F-REFRESH-WRITETHROUGH), and owning the whole file would restate and freeze Omarchy's seeded defaults, against the deltas-only rule (D-DELTA-STORAGE).

Decision Choice Why
D-CLAUDE-CONFIG Track Claude Code's custom config Consolidate the two genuine custom-config artifacts under ~/.claude, split by how Claude Code treats them. statusline-command.sh (a self-contained, theme-aware prompt script Claude never rewrites) is stowed via a new claude package, like tmux/local.conf. settings.json is instead applied as an idempotent jq delta (claude/settings.jq + apply_jq_deltas) that install overlays onto the live file, seeding {} first so a pre-first-run box still converges. Because that filter is a build input read in place — not a dotfile — a claude/.stow-local-ignore keeps stow from symlinking it into $HOME (it sits at the package root, so it would otherwise land at ~/settings.jq). verify.sh link-checks the script and confirms the settings overlay landed. Tool-rewritten JSON gets a delta, not a symlink. Claude Code rewrites settings.json itself (via /config), so stowing it risks the same write-through / rename-detach failure that keeps Omarchy-owned files off symlinks (F-REFRESH-WRITETHROUGH); asserting only our keys via jq preserves anything Claude adds and re-converges every run — the same trade as D-WAYBAR-DELTAS. The repo therefore never contains settings.json, only the filter, so no credential or machine state can leak. Everything else under ~/.claude is secrets/state/cache (.credentials.json, ~/.claude.json, projects/ transcripts + auto memory, history, caches, sessions) and is deliberately excluded — nothing there is tracked.
