Decision Log

Decisions & rationale

Every load-bearing choice, with the reason it was made. Each has a stable ID (see Trace); the D-ID tags below are grep targets.

Core architecture

Decision Choice Why
D-ENGINE Convergence engine Lightweight shell + Omarchy CLI + stow. No Ansible, no dot-apply/check/update/cleanup engine. Omarchy already does install/seed/migrate/update. A convergence framework would re-implement that and accrue code that must survive upstream churn.
D-SCRIPTS-MINIMAL Scripts One script: install. No update/cleanup scripts. Owner chose pure-minimal. Updates run via omarchy update -y; one-time i3/zsh cleanup is a documented manual step.
D-DELTA-STORAGE Delta storage Own thin fragments + single managed integration block. Never symlink Omarchy-owned files. (Full detail: Architecture.) Omarchy cp-resets write through symlinks (F-REFRESH-WRITETHROUGH); owning whole files freezes them and breaks on the coming Lua move (F-LUA).

Repo hygiene & CI

Decision Choice Why
D-CI Makefile = ops interface A root Makefile is the single source of truth for repo operations. GitHub Actions (.github/workflows/ci.yml) invokes the same targets, so make ci == CI. Targets:
  • make ci — gates: shellcheck + shfmt (-i 2 -ci) on the shell set, pinned prettier on docs HTML/JSON, an empty-object smoke-check of every waybar/*.jq filter (so jq syntax/behavior bugs surface here rather than at ./install time), and .github/scripts/check_docs.py for docs integrity. make fmt auto-fixes.
  • make update — chained refresh of everything package-manager-reachable: omarchy update -y (pacman + AUR + omarchy migrations) + omarchy update firmware (fwupd) + uv self update, then make verify. Each step is warn-on-failure so a non-zero exit (no firmware devices, reboot decline, etc.) doesn't silently skip the rest.
  • make verify — read-only live health check (.github/scripts/verify.sh): hyprctl configerrors, all five managed blocks present (bashrc, hypr, keymaps, tmux, waybar style.css), stow links resolve into the repo (including dangling detection), dev-env tools on PATH and not pacman-owned, XDG state, and the default-tracking override comparison (border_size = 2 vs omarchy's looknfeel.conf default — see D-LOOKNFEEL).
Tooling is Omarchy-native and version-pinned. 		One interface for humans and agents; CI calling the Makefile means the two can't drift. The docs checker turns the traceability discipline (registry ↔ anchors ↔ [ID] code tokens, links, appears_in) into an enforced invariant rather than a convention. The Makefile is dev/ops tooling; the lone runtime script is still install (D-SCRIPTS-MINIMAL).
D-DEV-ENV dev-env reconcile uv and go are owned by Omarchy's omarchy install dev-env <kind> path, not by pacman/AUR or hand-rolled installers. ./install's ensure_dev_env_tool helper actively reconciles: if pacman owns the tool, omarchy pkg drop it (graceful on dep-conflict refusal); if not on PATH, install via omarchy install dev-env. No path pinning — omarchy lands each tool wherever the underlying installer defaults today (Astral's ~/.local/bin/uv; mise's ~/.local/share/mise/shims/go) and command -v finds it. The user's rule: if a tool is installed in a way the repo doesn't declare, it should get replaced. Reconciling on ./install enforces that for the main drift vector (pacman) while staying robust to upstream path changes. Latest-at-bootstrap caveat: omarchy install dev-env pulls latest at the time it runs (mise @latest, Astral installer), so a fresh bootstrap on different days may yield different versions; make update is the deliberate bumper.
D-PKG-REMOVE Subtractive baseline overlay Three coupled curation mechanisms that each subtract from the post–Remove-Preinstalled baseline.
  • packages.remove.txt — symmetric subtractive partner to packages.txt / packages.aur.txt, processed via omarchy pkg drop after both add steps so a name in both files resolves to "removed". Wrapped in warn-and-continue because pacman -Rns can refuse on reverse-dep conflicts. Empty list → no-op; already-absent names → no-op at the omarchy CLI layer. Scope: pacman-tracked only (official-repo + AUR). Web apps are not pacman packages; remove those with omarchy webapp remove.
  • elephant/.config/elephant/websearch.toml — stowed override of elephant's compiled-in default web-search entry (Google). Walker's app picker queries elephant; the TOML override is the elephant-generated, elephant-doc'd way to set custom engines. Defaults to DuckDuckGo here.
  • Stale-launcher cleanup in install — explicit rm -f for known orphan ~/.local/share/applications/*.desktop files whose underlying package is gone but the user-dir launcher remained (pacman -Rns only removes files the package installed, not user-state files copied there later).
The repo's overlay surface was previously additive-only for packages and silent on user-state under ~/.local/share/applications/ and ~/.config/elephant/. The "Deeper package cleanup" backlog wanted a way to express "drop this omarchy default" without depending on the one-shot Remove Preinstalled menu (per D-BASELINE, that menu action is the documented manual prerequisite, not a substitute for ongoing curation). One token, three mechanisms — because they share the same intent (subtract from baseline) but live on different surfaces (pacman db, stowed config, user-state launchers). Audit rule: before adding a name to packages.remove.txt, grep ~/.local/share/omarchy/ for usage — omarchy wires some "builtins" into keybindings or shell init (e.g. zoxide → cd alias, fzf → keybindings, btop → SUPER+T). Removing one of those silently breaks omarchy commands; cleanup the wiring in our overlay at the same time (e.g. the matching unbind in hypr.conf when we dropped btop).

Shell

Decision Choice Why
D-SHELL-BASH Login shell bash (Omarchy default). No chsh to zsh. Omarchy's boot/session/helpers assume bash; chsh→zsh is a documented footgun (F-SHELL-RESEARCH). Omarchy's bash already wires starship/zoxide/fzf/mise, so zsh's marginal gain is small.
D-SHELL-SEAM Aliases/functions Ported into ~/.config/dotfiles/shell.sh, sourced via the ~/.bashrc managed block (at EOF, so ours win). ~/.bashrc is owner-owned and "not overwritten on updates" (F-BASH-CHAIN). Aliases Omarchy already defines (t, g, gcm, gcam, n, cd/zoxide, ls/eza) are dropped in favor of Omarchy's.
D-SECRETS-LOCAL Secrets/host-specific Gitignored shell.local.sh (Vertex project IDs, device serials). Keep the shared repo generic and secret-free.

Hyprland deltas (i3 "spirit", confirmed item-by-item)

Most i3 customizations were already done or native on Omarchy (key-repeat, touchpad scroll, thin borders, move-ws-to-monitor, volume/brightness/screenshot/lock keys, launcher, wallpaper). Only three were genuine:

Delta Status Notes
D-CAPS-CTRL caps lock → control in (fragment) Moved off Omarchy's seeded input.conf into the owned fragment, sourced last.
D-WORKSPACE-RULES Workspace app-assignments in windowrule = workspace N (terminal→1, Firefox→2, Slack+Obsidian→3, IntelliJ→5, Spotify→10). Verify classes via hyprctl clients.
D-SCREENSHOT-FALLBACK Screenshot fallback in (fragment) SUPER+SHIFT+S invokes omarchy-capture-screenshot while the keyboard's physical PRINT key emits no Linux input event. Omarchy's stock PRINT binding stays intact; the fallback uses a live-conflict-checked key and remains easy to remove when firmware/profile behavior is fixed.
D-MOUSE-ACCEL External MX Master mouse accel in (local) Device-specific → gitignored hypr.local.conf.
D-HJKL-DECLINED vim hjkl window focus declined Would require unbinding Omarchy's SUPER+J/SUPER+L. Keep Omarchy's SUPER+arrows.
D-LOOKNFEEL Looknfeel deltas in (fragment) Three overlay-sourced-last deltas to omarchy's looknfeel chain: (1) general { border_size = 2 } so the window-no-gaps toggle keeps killing gaps without also killing borders — this is the single line in any overlay that re-states an omarchy default value (border_size = 2 in looknfeel.conf) because a downstream toggle would otherwise zero it, so make verify compares the two and fails loudly if omarchy ever moves their default; (2) windowrule = rounding 8, match:float 1 — same windowrule grammar omarchy uses for tagged popups (rounding 8, match:tag pop in default/hypr/apps/system.conf), but state-based on the floating bit instead of a tag, so tiles stay square (omarchy global default) and any floating window rounds; (3) decoration { blur { size = 8; brightness = 0.72 } } plus windowrule = opacity 0.86 0.78, match:tag terminal so terminals get a mild frosted-glass effect without hard-coding terminal colors or breaking omarchy theme swaps. Edits to ~/.config/hypr/looknfeel.conf wouldn't fix the border problem because that file loads before the window-no-gaps toggle in hyprland.conf's source chain — only an overlay sourced after the toggle can win, which is exactly what our fragment is. See F-HYPR-SEAM for the full ordering.
D-MONITORS Docked dual-monitor layout in (fragment) Two monitor = lines in the overlay encode the dock layout: DP-5 (Acer XV272U) primary at 0x0, DP-4 (Acer XV272U V) secondary at 1920x0, both at native 2560×1440 @ 144 Hz and compositor scale 1.333333 (effective logical 1920×1080 per panel — the secondary's position is in scaled pixels, hence 1920x0 rather than 2560x0; see F-MONITOR-SCALE-PERSIST for why we set the scale in the overlay rather than via the Super + / cycle). Matched by full desc: identifier (description string up to but not including the trailing portname, per the Hyprland wiki — see F-MONITOR-RULE-APPLY) so cable-swaps between DP ports don't change the layout. The full serial tail is load-bearing because both Acer descriptions share the Acer Technologies XV272U prefix — a panel swap (same model, new EDID serial) silently falls through to the omarchy wildcard, so update the desc: string when that happens. No hot-plug script: Hyprland re-applies monitor = rules on every monitor connect, which is the same matcher behavior that makes omarchy's seeded fallback monitor=,preferred,auto,auto work; the omarchy-shipped omarchy-hyprland-monitor-watch already covers removal recovery. No workspace = N, monitor:… pins — on a fresh session, Hyprland assigns workspace 1 to the leftmost monitor by position (DP-5 at 0x0), which is what "primary" means here (Hyprland has no xrandr-style primary concept). One nuance: when these rules first land via hyprctl reload on a running session, the existing workspace→monitor bindings are preserved — workspace 1 stays on whichever monitor it was on, and fully migrates only on next fresh login (or move it now with hyprctl dispatch movecurrentworkspacetomonitor DP-5). Install restarts waybar on topology change: install's validation block snapshots hyprctl monitors around the post-stow hyprctl reload (extracting name/position/mode/disabled per output) and, if the snapshot diff is non-empty, invokes omarchy-restart-waybar with the same poll-and-confirm pattern as the waybar-overlay restart. Waybar's per-output bars don't always survive a layout flip; this is the integration step that makes a fresh ./install after a monitor = edit reach a fully-rendered desktop without a manual restart. eDP-1 is deliberately not in the overlay: omarchy's lid-switch handler at default/hypr/bindings/utilities.conf calls omarchy-hyprland-monitor-internal off/on, which writes monitor=eDP-1,disable to ~/.local/state/omarchy/toggles/hypr/internal-monitor-disable.conf. Our overlay loads after the toggles (F-HYPR-SEAM), so an explicit eDP-1 rule here would silently beat the toggle. The wildcard monitor=,preferred,auto,auto already activates eDP-1 at its only supported mode (1920×1200 @ 120 Hz) when the toggle isn't present. Same load-order pattern as D-LOOKNFEEL but inverted: silence to let the downstream toggle win, instead of re-stating to beat it. GDK_SCALE intentionally untouched: omarchy seeds env = GDK_SCALE,2 in monitors.conf (right for the laptop's 13"/2.8K panel). GDK_SCALE is process-global on Wayland — there is no per-monitor GTK scaling without per-app launchers — so dropping it to 1 for the 1440p externals would shrink GTK apps on eDP-1. The compositor scale 1 in our two monitor = lines is the in-scope correctness step; the GTK-oversize trade on the externals is acceptable until per-app launchers become worth it. Forward risk: when omarchy ships the Lua hyprland config (F-LUA), these two lines become two hl.monitor({…}) calls; the design is unaffected.

Waybar deltas

Waybar's config sits in ~/.config/waybar/config.jsonc, an omarchy-seeded file that the live system mutates two different ways (F-WAYBAR-MIGRATIONS). Omarchy's manual recommends direct edits and treats periodic .bak restores as the recovery story; this repo applies D-DELTA-STORAGE to JSON instead: own thin deltas, re-apply them every ./install, restart only on real change.

Decision Choice Why
D-WAYBAR-DELTAS Waybar overlay shape Two coupled overlays: waybar/deltas.jq holds personal config.jsonc deltas as composed jq filters; a managed block in style.css (via the existing upsert_block helper) carries the matching CSS rules. install's apply_jq_deltas applies the jq filters idempotently; the style block is re-anchored at EOF the same way as the bashrc/hyprland/tmux/keymaps blocks. waybar is only restarted when content actually changed (hash-compare around both files), and the restart waits-and-polls pgrep -x waybar to verify the process actually came back. Initial deltas: drop the 1-5 persistent-workspaces pin so workspaces grow on demand (i3-style), add an icon-only memory module on the same 5 s nominal interval as cpu (with used/total/% in tooltip-format on hover), and extend omarchy's #cpu, #battery, ... CSS spacing rule to include #memory so the new module renders with the same margins as its neighbors. Spacing rationale: omarchy ships an asymmetric right side — #custom-expand-icon has margin-right: 18 px, #bluetooth 17 px, #tray 16 px, #network 13 px, while #cpu/#battery/#pulseaudio share margin: 0 7.5 px and #memory gets no rule at all. We flatten every right-side module to margin: 0 4 px on each side (equidistant ~8 px gaps, snug but not pinched). The override wins via CSS's later-rule-wins ordering — our managed block sits at EOF of style.css, after omarchy's per-module rules. Forking the whole file would silently drop every future surgical migration (F-WAYBAR-MIGRATIONS); direct edits would be wiped on the next omarchy-refresh-waybar and only recoverable through a .bak diff. Owning only the deltas survives both mutation patterns: refresh overwrites get re-patched on next install, surgical migrations either pre-date our filter or touch keys our filter doesn't (the memory module uses a merge pattern so future upstream keys survive). Each delta was battery-audited: memory uses the same 5 s nominal interval as cpu — waybar runs per-module timers independently so this isn't strict coalescing, but it's the cheapest practical cadence. A verbose 1 s clock tick was considered and deliberately rejected because it would prevent deep C-states.

Baseline & bindings.conf D-BASELINE

Reference baseline = "Omarchy after Remove Preinstalled" The owner's first step was running Remove Preinstalled, which stripped bundled apps and their launcher bindings (F-BASELINE). So the trimmed ~/.config/hypr/bindings.conf is intentional, not drift. We leave it Omarchy-owned and untracked; we do not restore it to vanilla stock. Reproduction recipe: install → Remove Preinstalled → ./install.
