Decision Log

Decisions & rationale

Every load-bearing choice, with the reason it was made. Each has a stable ID (see Trace); the D-ID tags below are grep targets.

Core architecture

Decision Choice Why
D-ENGINE Convergence engine Lightweight shell + Omarchy CLI + stow. No Ansible, no dot-apply/check/update/cleanup engine. Omarchy already does install/seed/migrate/update. A convergence framework would re-implement that and accrue code that must survive upstream churn.
D-SCRIPTS-MINIMAL Scripts One convergence script: install. User commands may be stowed under bin/.local/bin, but package updates and cleanup remain explicit operator actions. Owner chose pure-minimal. Updates run via make update / omarchy update -y; package cleanup uses packages.remove.txt plus read-only audits such as pkg-residue, not an automatic cleanup engine.
D-DELTA-STORAGE Delta storage Own thin fragments + single managed integration block. Never symlink Omarchy-owned files. (Full detail: Architecture.) Omarchy cp-resets write through symlinks (F-REFRESH-WRITETHROUGH); owning whole files freezes them and breaks on the coming Lua move (F-LUA).

Repo hygiene & CI

Decision Choice Why
D-CI Makefile = ops interface A root Makefile is the single source of truth for repo operations. GitHub Actions (.github/workflows/ci.yml) invokes the same targets, so make ci == CI. Targets:
  • make ci — gates: shellcheck + shfmt (-i 2 -ci) on the shell set, pinned prettier on docs HTML/JSON, an empty-object smoke-check of every tracked jq delta plus a duplicate-repair/fixed-point fixture for the Quickshell layout (so jq syntax and convergence bugs surface here rather than at ./install time), and .github/scripts/check_docs.py for docs integrity. make fmt auto-fixes.
  • make update — the frequent, low-risk channel: omarchy update -y (pacman + AUR + omarchy migrations and Quattro-owned mise agent updates), then uv self update because uv remains outside mise, then make verify. It first refuses while pacman -Qdtq reports orphans, avoiding the updater's pseudo-TTY prompt after Elephant retirement. Non-zero Omarchy or uv update exits are warned, then the wrapper continues through the remaining channel and read-only verification so independent drift is still reported.
  • make update-firmware — firmware only: omarchy update firmware (fwupd). It is the lone opt-in channel because firmware alone — unlike packages or the self-managed tools folded into make update — has device-specific prompts and reboot/power-cycle outcomes.
  • make verify — read-only live health check (.github/scripts/verify.sh): hyprctl configerrors, the five managed seams (bashrc, Hypr Lua, keymaps, tmux, starship), Quickshell plugin/layout/command checks, terminal and browser convergence, D-TERM-GHOSTTY), stow links resolve into the repo (including the uwsm/env.d SSH-agent fragment and dangling detection), mise agent wrappers, dev-env tools, XDG/SSH state, and live Hypr appearance values (see D-LOOKNFEEL).
  • make pkg-residue PACKAGE=<name> — wrapper around the stowed pkg-residue command for read-only package-leftover audits.
Tooling is Omarchy-native and version-pinned. 		One interface for humans and agents; CI calling the Makefile means the two can't drift. The docs checker turns the traceability discipline (registry ↔ anchors ↔ [ID] code tokens, links, appears_in) into an enforced invariant rather than a convention. The Makefile is dev/ops tooling; the lone runtime script is still install (D-SCRIPTS-MINIMAL).
D-DEV-ENV dev-env reconcile uv and go are owned by Omarchy's omarchy install dev-env <kind> path, not by pacman/AUR or hand-rolled installers. ./install's ensure_dev_env_tool helper actively reconciles: if pacman owns the tool, omarchy pkg drop it (graceful on dep-conflict refusal); if not on PATH, install via omarchy install dev-env. No path pinning — omarchy lands each tool wherever the underlying installer defaults today (Astral's ~/.local/bin/uv; mise's ~/.local/share/mise/shims/go) and command -v finds it. The user's rule: if a tool is installed in a way the repo doesn't declare, it should get replaced. Reconciling on ./install enforces that for the main drift vector (pacman) while staying robust to upstream path changes. Latest-at-bootstrap caveat: omarchy install dev-env pulls latest at the time it runs (mise @latest, Astral installer), so a fresh bootstrap on different days may yield different versions; make update runs uv self update; Quattro's main updater owns mise-backed tool and agent upgrades.
D-OPENCODE-LSP Global OpenCode LSP Keep Omarchy's seeded ~/.config/opencode/opencode.json, then use opencode/settings.jq to assert only "lsp": true. This enables every built-in server globally while preserving Omarchy defaults and unrelated user keys. Do not install a blanket system LSP bundle: OpenCode lazily starts matching servers and auto-installs many of them; runtimes and project-coupled servers remain with their projects or Omarchy's install dev-env path. OpenCode's current behavior is applicability-based, not a quality ranking: it starts all enabled servers whose extension, root-marker, and executable requirements match an opened file. A global setting applies from every launch directory, but cannot promise one objectively “best” server in every folder: project config may override global config, root discovery is bounded by the OpenCode instance/worktree, and missing SDKs or project dependencies can prevent a match. See F-OPENCODE-LSP.
D-PKG-REMOVE Baseline package/app curation Keep stock Quattro, then apply explicit deltas. packages.txt and packages.aur.txt add genuine extras; packages.remove.txt is the persistent deny-list applied with omarchy pkg drop. The broad Remove Preinstalled flow is not used because it also removes retained Quattro apps, OmaCalc, and agent wrappers.
  • packages.txt / packages.aur.txt — additive extras, processed through omarchy pkg add / omarchy pkg aur add. Coding agents and Obsidian are omitted because Quattro owns them. App channel choices follow the Omarchy-native audit in F-APP-CHANNELS: spotify uses Quattro's sync-repo service package, and slack-desktop is an intentional local AUR choice because Omarchy has no Slack package, webapp, binding, or migration. Operator CLI utilities use the same official-repository path: nmap comes from Arch extra through packages.txt. Security tooling follows F-MALWARE-SCANNER: clamav comes from Arch extra through packages.txt, while signature refreshes and scans remain explicit operator actions with no background daemon enabled.
  • packages.remove.txt — symmetric subtractive partner to packages.txt / packages.aur.txt, processed via omarchy pkg drop after both add steps so a name in both files resolves to "removed". Wrapped in warn-and-continue because pacman -Rns can refuse on reverse-dep conflicts. Empty list → no-op; already-absent names → no-op at the omarchy CLI layer. Scope: pacman-tracked only (official-repo + AUR). Web apps are not pacman packages; remove those with omarchy webapp remove.
  • Stale-launcher cleanup in install — explicit rm -f for known orphan ~/.local/share/applications/*.desktop files whose underlying package is gone but the user-dir launcher remained (pacman -Rns only removes files the package installed, not user-state files copied there later).
  • bin/.local/bin/pkg-residue — read-only audit for package leftovers after removal. It derives search terms from the package name and any known pacman/cache file list, uses rg --files as the fast path for file matches, uses find -type d for directory matches, filters paths owned by pacman, and reports likely residual user state, system state, and package cache entries without deleting anything.
A major upgrade can reinstall base packages and mark them explicit, so the deny-list is durable desired state rather than a one-time cleanup. install seeds a missing mutable OpenCode config only to apply the user's LSP delta; Quattro still owns the OpenCode binary through its mise wrapper. The installer removes legacy opencode/claude-code pacman packages only when an interrupted or manual transition leaves them behind; this mirrors Quattro's upgrade cleanup and does not alter its mise wrappers or user config. Audit rule: before adding a name to packages.remove.txt, grep /usr/share/omarchy/ for usage — Omarchy wires some "builtins" into keybindings or shell init (e.g. zoxide → cd alias, fzf → keybindings, btop → SUPER+CTRL+T). Removing one of those silently breaks omarchy commands, so clean up the matching wiring in our overlay in the same change (e.g. an hl.unbind in hypr/dotfiles.lua for a keybound tool — which is exactly why btop and eza are not dropped: btop is keybound and eza backs the ls alias).
D-WEBAPP Webapp ownership retired No repository implementation remains. Quattro packages the Zoom desktop entry with the needed protocol handlers and refreshes applications through its native lifecycle. Restating a packaged Quattro launcher would violate the deltas-only rule and create two owners. The historical ID remains so earlier trace links continue to resolve.
D-BROWSER-DEFAULT Default browser Stable Brave Origin is the converged default browser. install calls omarchy install browser brave-origin only when the package is absent and omarchy default browser brave-origin only when the selected default differs. It verifies the resulting state, then asserts the additional HTML and scheme MIME handlers that xdg-settings does not cover. Quattro natively maps Brave Origin to stable, owns its flags, extensions, policies, and theme refresh. The repository hook and package/channel compatibility code are therefore deleted. The command's desktop notification can fail after state succeeds, so the following read-only default assertion is the safety gate.

Shell

Decision Choice Why
D-SHELL-BASH Login shell bash (Omarchy default). No chsh to zsh. Omarchy's boot/session/helpers assume bash; chsh→zsh is a documented footgun (F-SHELL-RESEARCH). Omarchy's bash already wires starship/zoxide/fzf/mise, so zsh's marginal gain is small.
D-SHELL-SEAM Aliases/functions Ported into ~/.config/dotfiles/shell.sh, sourced via the ~/.bashrc managed block (at EOF, so ours win). ~/.bashrc is owner-owned and "not overwritten on updates" (F-BASH-CHAIN). Aliases Omarchy already defines (t, g, gcm, gcam, n, cd/zoxide, ls/eza) are dropped in favor of Omarchy's.
D-SECRETS-LOCAL Secrets/host-specific Gitignored shell.local.sh holds personal and device-specific aliases, functions, and keybinds (Vertex project IDs, device serials, the Ctrl-F sessionizer bind, VPN/GCP helpers) — never install-path redirects, since Omarchy installs tools (uv, gcloud, …) natively on PATH. Keep the shared repo generic and secret-free.

Delta Status Notes
D-CAPS-CTRL caps lock → control in (fragment) Moved off Omarchy's seeded input.conf into the owned fragment, sourced last.
D-WORKSPACE-RULES Workspace app-assignments in windowrule = workspace N (terminal→1, Brave Origin→2, Slack+Obsidian→3, IntelliJ→5, Spotify→10). Verify classes via hyprctl clients.

D-LOOKNFEEL Looknfeel deltas in (fragment) An always-on "compact look" in the reloadable personal Lua module: (1) general { gaps_in = 2; gaps_out = 4 } — slim but present gaps (omarchy's defaults are 5/10); (2) general { border_size = 2 } so the window-no-gaps toggle keeps killing gaps without also killing borders — this is the single line in any overlay that re-states an omarchy default value (border_size = 2 in looknfeel.conf) because that downstream toggle would otherwise zero it, so make verify compares the two and fails loudly if omarchy ever moves their default; (3) decoration { rounding = 8 } — every corner rounds at omarchy's documented radius (the commented rounding = 8 hint in its looknfeel.conf template, and the same radius omarchy applies to popups via rounding 8, match:tag pop in default/hypr/apps/system.conf); (4) decoration { blur { enabled = true; size = 8; passes = 2; brightness = 0.72; contrast = 0.75 } } plus explicit shadow enablement because Quattro disables both effects by default, and plus a narrow terminal-class opacity rule at 0.86/0.78 so terminals get a mild frosted-glass effect without hard-coding terminal colors or breaking omarchy theme swaps; (5) misc { focus_on_activate = false } so an app's activation request (chat message, browser opening a link, a finished build) only marks the window urgent instead of stealing focus and jumping you to its workspace — omarchy sets this true in default/hypr/looknfeel.conf whereas Hyprland's own default is false, so this inverts an omarchy non-default rather than re-stating a default (no make verify guard needed, unlike border_size). Because the fragment is sourced after both omarchy's defaults and the window-no-gaps toggle in hyprland.conf's source chain, these values win regardless of toggle state — editing ~/.config/hypr/looknfeel.conf wouldn't, since it loads before the toggle. See F-HYPR-SEAM for the full ordering.
D-MONITORS Known external monitor layouts in (fragment) Three monitor = lines in the overlay encode known external displays. The home dock layout is: DP-5 (Acer XV272U) primary at 0x0, DP-4 (Acer XV272U V) secondary at 1920x0, both at native 2560×1440 @ 144 Hz and compositor scale 1.333333 (effective logical 1920×1080 per panel — the secondary's position is in scaled pixels, hence 1920x0 rather than 2560x0; see F-MONITOR-SCALE-PERSIST for why we set scale in the overlay rather than via the Super + / cycle). The work monitor is DP-1 (Dell U2719DC) at 0x0, native 2560×1440 @ 59.95 Hz, compositor scale 1.25; its EDID advertises no higher-refresh native mode, so this rule favors the best-quality native resolution over lower resolution 75 Hz fallbacks. All are matched by full desc: identifier (description string up to but not including the trailing portname, per the Hyprland wiki — see F-MONITOR-RULE-APPLY) so cable-swaps between DP ports don't change the layout. The full serial tail is load-bearing because both Acer descriptions share the Acer Technologies XV272U prefix — a panel swap (same model, new EDID serial) silently falls through to the omarchy wildcard, so update the desc: string when that happens. No hot-plug script: Hyprland re-applies monitor = rules on every monitor connect, which is the same matcher behavior that makes omarchy's seeded fallback monitor=,preferred,auto,auto work; the omarchy-shipped omarchy-hyprland-monitor-watch already covers removal recovery. No workspace = N, monitor:… pins — on a fresh session, Hyprland assigns workspace 1 to the leftmost monitor by position (DP-5 at 0x0), which is what "primary" means here (Hyprland has no xrandr-style primary concept). One nuance: when these rules first land via hyprctl reload on a running session, the existing workspace→monitor bindings are preserved — workspace 1 stays on whichever monitor it was on, and fully migrates only on next fresh login (or move it now with hyprctl dispatch movecurrentworkspacetomonitor DP-5). eDP-1 is deliberately not in the overlay: omarchy's lid-switch handler at default/hypr/bindings/utilities.conf calls omarchy-hyprland-monitor-internal off/on, which writes monitor=eDP-1,disable to ~/.local/state/omarchy/toggles/hypr/internal-monitor-disable.conf. Our overlay loads after the toggles (F-HYPR-SEAM), so an explicit eDP-1 rule here would silently beat the toggle. The wildcard monitor=,preferred,auto,auto already activates eDP-1 at its only supported mode (1920×1200 @ 120 Hz) when the toggle isn't present. Same load-order pattern as D-LOOKNFEEL but inverted: silence to let the downstream toggle win, instead of re-stating to beat it. GDK_SCALE intentionally untouched: omarchy seeds env = GDK_SCALE,2 in monitors.conf (right for the laptop's 13"/2.8K panel). GDK_SCALE is process-global on Wayland — there is no per-monitor GTK scaling without per-app launchers — so dropping it to 1 for the 1440p externals would shrink GTK apps on eDP-1. The compositor scale in our monitor = lines is the in-scope correctness step; the GTK-oversize trade on the externals is acceptable until per-app launchers become worth it. Forward risk: when omarchy ships the Lua hyprland config (F-LUA), these lines become hl.monitor({…}) calls; the design is unaffected.
D-KINESIS-REMAP Kinesis Adv360 SmartSet thumb remap done Profile-1 thumb cluster reworked for Omarchy's SUPER-centric binds: SUPER on both bottom thumb keys ([end]>[lwin], [pgdn]>[rwin]) for either-hand chording; Alt moved to the freed inner-right key ([rwin]>[ralt]); Home→Tab ([home]>[tab]) so SUPER/ALT+Tab are thumb gestures; and Calc→F14 ([pgup]>[f14]) bound by keycode (code:192, since F13+ keysyms map unreliably through xkb) to the clipboard manager. Caps left as-is; Delete stays on the fn layer. Layout backed up at kinesis/layout1.txt.

Quickshell deltas (historical Waybar ID)

Quattro retires Waybar, Walker, and Elephant. The current overlay uses a supported Quickshell plugin for dynamic workspaces, a command module for memory, shell.toml for the exact urgent/active color, and a narrow shell.json delta applied through omarchy-shell-config. The stable ID below is kept for trace continuity. The remaining v3 detail is historical context only.

Historically, Waybar's config sat in ~/.config/waybar/config.jsonc, an omarchy-seeded file that the live system mutates two different ways (F-WAYBAR-MIGRATIONS). Omarchy's manual recommends direct edits and treats periodic .bak restores as the recovery story; this repo applies D-DELTA-STORAGE to JSON instead: own thin deltas, re-apply them every ./install, restart only on real change.

Decision Choice Why
D-QUICKSHELL-DELTAS Quickshell overlay shape Stow the supported user-owned pashbyl.workspaces plugin, memory command, and shell.toml. Keep shell.json mutable and converge only module IDs and ordering with omarchy/shell.jq through the official omarchy-shell-config normalize/commit helpers. The filter removes every stock or personal workspace entry before inserting exactly one personal entry after the menu, so upstream re-additions and interrupted runs converge to the same state. Quattro documents plugins as the supported widget seam, while shell.json has no deep-merge facility and is replaced by the upgrade. A narrow, fixed-point jq delta preserves upstream modules and repairs duplicates without forking Omarchy's shell.
D-WAYBAR-DELTAS Historical Waybar overlay Retired v3 implementation details: Two coupled overlays: waybar/deltas.jq holds personal config.jsonc deltas as composed jq filters; a managed block in style.css (via the existing upsert_block helper) carries the matching CSS rules. install's apply_jq_deltas applies the jq filters idempotently; the style block is re-anchored at EOF the same way as the bashrc/hyprland/tmux/keymaps blocks. waybar is only restarted when content actually changed (hash-compare around both files), and the restart waits-and-polls pgrep -x waybar to verify the process actually came back. Initial deltas: drop the 1-5 persistent-workspaces pin so workspaces grow on demand (i3-style), add an icon-only memory module on the same 5 s nominal interval as cpu (with used/total/% in tooltip-format on hover), and extend omarchy's #cpu, #battery, ... CSS spacing rule to include #memory so the new module renders with the same margins as its neighbors. Urgent workspaces: omarchy ships no urgent styling, and its #workspaces button { all: initial } reset means a workspace flagged urgent shows nothing — so with focus_on_activate off a window requesting attention would be invisible. The block adds a #workspaces button.urgent label rule that recolors the workspace digit to a muted red #a55555 — the same attention accent the bar already uses for its screen-record/idle/notify-silence indicators — reproducing i3's number-color cue. It targets the label node because omarchy's global * { color: @foreground } paints the digit directly, overriding a button-only color rule. The color is a literal for the same reason as the tray accent below — waybar CSS only receives @foreground/@background, never the theme's per-theme accent. Spacing rationale: omarchy ships an asymmetric right side — #custom-expand-icon has margin-right: 18 px, #bluetooth 17 px, #tray 16 px, #network 13 px, while #cpu/#battery/#pulseaudio share margin: 0 7.5 px and #memory gets no rule at all. We flatten every right-side module to margin: 0 4 px on each side (equidistant ~8 px gaps, snug but not pinched). The override wins via CSS's later-rule-wins ordering — our managed block sits at EOF of style.css, after omarchy's per-module rules. Tray menu hover: the same block also restores the right-click tray (dbusmenu) context-menu hover highlight. omarchy's * { background-color: @background } reset loads at GTK application priority, beating the theme's menuitem:hover by priority rather than specificity — so hovered rows never highlighted. Worse, that reset paints an opaque @background box on every node, including each menuitem's label, so a row-level highlight would only show at the edges with a dark box behind the text. The fix is two same-sheet rules that win by specificity: clear the box on the menuitem content nodes (label/arrow/check/radio → background-color: transparent), then tint the hovered row with alpha(@theme_selected_bg_color, 0.4). The tint — rather than a solid fill with a foreground/background flip — keeps the menu's dark base so the unchanged light text stays readable; the label-color override a solid highlight would need doesn't take in GTK3's menu nodes (the text rendered invisible). @theme_selected_bg_color is GTK's built-in selection accent (always defined), so it gives a distinct hue without hardcoding. omarchy exposes only @foreground/@background to waybar CSS and keeps its per-theme accent (#7aa2f7 for Tokyo Night) in colors.toml, which GTK CSS can't read — matching the accent per-theme would need a separate theme-set hook bridge, out of scope for a tray highlight. Forking the whole file would silently drop every future surgical migration (F-WAYBAR-MIGRATIONS); direct edits would be wiped on the next omarchy-refresh-waybar and only recoverable through a .bak diff. Owning only the deltas survives both mutation patterns: refresh overwrites get re-patched on next install, surgical migrations either pre-date our filter or touch keys our filter doesn't (the memory module uses a merge pattern so future upstream keys survive). Each delta was battery-audited: memory uses the same 5 s nominal interval as cpu — waybar runs per-module timers independently so this isn't strict coalescing, but it's the cheapest practical cadence. A verbose 1 s clock tick was considered and deliberately rejected because it would prevent deep C-states.

Terminal (Ghostty default)

Decision Choice Why
D-TERM-GHOSTTY Ghostty is the default terminal; Alacritty removed install installs Ghostty only when its package is absent, selects it with omarchy default terminal only when the default differs, and adds alacritty to packages.remove.txt. The omarchy CLI is the whole mechanism: it installs the package, seeds ~/.config/ghostty when missing, and rewrites ~/.config/xdg-terminals.list — whose first entry is the sole definition of the default terminal (Super+Return goes through xdg-terminal-exec). The install step runs before the package drop so the list never points at an already-removed terminal. Separate package and default guards make re-runs idempotent while still repairing either half of the state independently. The commands' notification tails are fail-open; a following read-only default assertion is the safety gate. After the package drop, install also removes Omarchy migration 1763558828's user-owned ~/.local/share/applications/Alacritty.desktop when it exists; pacman does not own or remove the override. No terminal config is carried — Omarchy seeds ghostty, and ghostty's default right-click is a context menu (not paste), so the former Alacritty right-click no-op overlay was retired rather than ported. Letting the omarchy CLI own the desktop-entry id and the list is the delta-only, omarchy-native path (D-DELTA-STORAGE); hand-writing xdg-terminals.list would pin an omarchy-owned detail (com.mitchellh.ghostty.desktop). Removal uses the existing D-PKG-REMOVE mechanism because leaving an explicitly-unwanted package installed isn't "respecting defaults". The pre-removal audit confirmed Alacritty is safe to drop: Required By: None, omarchy-launch-screensaver dispatches on the actual default terminal (it has a ghostty branch), and every other omarchy script naming alacritty.toml is guarded by an [[ -f ]] test so it no-ops when the file is gone. The one durability caveat: a manual package-reinstall recovery flow (never omarchy update) reinstalls base packages including Alacritty; the package and migration-created launcher cleanup are idempotent, so re-running ./install re-drops both. make verify checks the default, package, and user launcher so this residue cannot pass unnoticed again.

Prompt (Starship) deltas

Decision Choice Why
D-STARSHIP-VENV Show the active Python venv name in the prompt A [custom.venv] module keyed on $VIRTUAL_ENV prints just the active venv's name (e.g. (.venv)) — and nothing when no venv is active, in any directory. Omarchy seeds a stripped format = "[$directory$git_branch$git_status]($style)$character". install inserts ${custom.venv} before $character (in-place, grep-guarded) and appends the module table as a standard upsert_block managed block that runs basename "$VIRTUAL_ENV" when $VIRTUAL_ENV is set, styled italic yellow. verify.sh greps the ${custom.venv} format reference and check_blocks the module. A $VIRTUAL_ENV-keyed custom module, not starship's native python module. The python module is starship's default venv display, but it only renders inside a detected Python-project directory and bundles via 🐍 <version>; the goal here is just the venv name, shown whenever a venv is active regardless of directory — exactly what a custom module on $VIRTUAL_ENV expresses. Storage is a hybrid in-place delta: the format reference must edit Omarchy's scalar format key — starship has no include and TOML can't merge two formats. D-QUICKSHELL-DELTAS sidesteps that wall with structured jq, but a format reference has no append or merge option, so this is a deliberate text-level sed — the repo's one in-place text edit. The module table, by contrast, is append-only and rides the standard managed block. Not stowed: ~/.config/starship.toml is seeded once (an Omarchy migration cps the default only if omarchy-cmd-missing starship), is never auto-refreshed, and only the manual omarchy refresh config starship.toml rewrites it — its cp -f would write through a stow symlink (F-REFRESH-WRITETHROUGH), and owning the whole file would restate and freeze Omarchy's seeded defaults, against the deltas-only rule (D-DELTA-STORAGE).

Claude Code config

Decision Choice Why
D-CLAUDE-CONFIG Track Claude Code's custom config Consolidate the two genuine custom-config artifacts under ~/.claude, split by how Claude Code treats them. statusline-command.sh (a self-contained, theme-aware prompt script Claude never rewrites) is stowed via a new claude package, like tmux/local.conf. settings.json is instead applied as an idempotent jq delta (claude/settings.jq + apply_jq_deltas) that install overlays onto the live file, seeding {} first so a pre-first-run box still converges. Because that filter is a build input read in place — not a dotfile — a claude/.stow-local-ignore keeps stow from symlinking it into $HOME (it sits at the package root, so it would otherwise land at ~/settings.jq). The default model and effort level are pinned as .env.ANTHROPIC_MODEL = "opus" and .env.CLAUDE_CODE_EFFORT_LEVEL = "xhigh" in the same overlay — not the top-level model / effortLevel keys: the /model and /effort pickers own and rewrite those keys (selecting Default even clears model), so a pinned key drifts on every switch, but neither picker touches .env, so the overlay stays a no-op. Claude Code applies its settings env block to the session (verified: it selects the model; CLAUDE_CODE_EFFORT_LEVEL is read from the env and is session-only), so these set the startup defaults while /model and /effort still switch at runtime. verify.sh link-checks the script and confirms the settings overlay landed (which covers the env pin). Tool-rewritten JSON gets a delta, not a symlink. Claude Code rewrites settings.json itself (via /config), so stowing it risks the same write-through / rename-detach failure that keeps Omarchy-owned files off symlinks (F-REFRESH-WRITETHROUGH); asserting only our keys via jq preserves anything Claude adds and re-converges every run — the same trade as D-QUICKSHELL-DELTAS. The repo therefore never contains settings.json, only the filter, so no credential or machine state can leak. Everything else under ~/.claude is secrets/state/cache (.credentials.json, ~/.claude.json, projects/ transcripts + auto memory, history, caches, sessions) and is deliberately excluded — nothing there is tracked.
