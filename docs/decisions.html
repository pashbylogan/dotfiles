Decision Log

Decisions & rationale

Every load-bearing choice, with the reason it was made. Each has a stable ID (see Trace); the D-ID tags below are grep targets.

Core architecture

Decision Choice Why
D-ENGINE Convergence engine Lightweight shell + Omarchy CLI + stow. No Ansible, no dot-apply/check/update/cleanup engine. Omarchy already does install/seed/migrate/update. A convergence framework would re-implement that and accrue code that must survive upstream churn.
D-SCRIPTS-MINIMAL Scripts One convergence script: install. User commands may be stowed under bin/.local/bin, but package updates and cleanup remain explicit operator actions. Owner chose pure-minimal. Updates run via make update / omarchy update -y; package cleanup uses packages.remove.txt plus read-only audits such as pkg-residue, not an automatic cleanup engine.
D-DELTA-STORAGE Delta storage Own thin fragments + single managed integration block. Never symlink Omarchy-owned files. (Full detail: Architecture.) Omarchy cp-resets write through symlinks (F-REFRESH-WRITETHROUGH); owning whole files freezes them and breaks on the coming Lua move (F-LUA).

Repo hygiene & CI

Decision Choice Why
D-CI Makefile = ops interface A root Makefile is the single source of truth for repo operations. GitHub Actions (.github/workflows/ci.yml) invokes the same targets, so make ci == CI. Targets:
  • make ci — gates: shellcheck + shfmt (-i 2 -ci) on the shell set, pinned prettier on docs HTML/JSON, an empty-object smoke-check of every tracked jq delta (so jq syntax errors surface here rather than at ./install time), and .github/scripts/check_docs.py for docs integrity. make fmt auto-fixes.
  • make update — the frequent, low-risk channel: omarchy update -y (pacman + AUR + omarchy migrations and Quattro-owned mise agent updates), then uv self update because uv remains outside mise, then make verify. It first refuses while pacman -Qdtq reports orphans, avoiding the updater's pseudo-TTY prompt. Non-zero Omarchy or uv update exits are warned, then the wrapper continues through the remaining channel and read-only verification so independent drift is still reported.
  • make update-firmware — firmware only: omarchy update firmware (fwupd). It is the lone opt-in channel because firmware alone — unlike packages or the self-managed tools folded into make update — has device-specific prompts and reboot/power-cycle outcomes.
  • make verify — read-only live health check (.github/scripts/verify.sh): hyprctl configerrors, the five managed seams (bashrc, Hypr Lua, keymaps, tmux, starship), Quickshell plugin and bar-layout checks, terminal and browser convergence, D-TERM-GHOSTTY), stow links resolve into the repo (including the uwsm/env.d SSH-agent fragment and dangling detection), mise agent wrappers, dev-env tools, XDG/SSH state, and live Hypr appearance values (see D-LOOKNFEEL).
  • make pkg-residue PACKAGE=<name> — wrapper around the stowed pkg-residue command for read-only package-leftover audits.
Tooling is Omarchy-native and version-pinned. 		One interface for humans and agents; CI calling the Makefile means the two can't drift. The docs checker turns the traceability discipline (registry ↔ anchors ↔ [ID] code tokens, links, appears_in) into an enforced invariant rather than a convention. The Makefile is dev/ops tooling; the lone runtime script is still install (D-SCRIPTS-MINIMAL).
D-DEV-ENV dev-env reconcile uv and go are owned by Omarchy's omarchy install dev-env <kind> path, not by pacman/AUR or hand-rolled installers. ./install's ensure_dev_env_tool helper actively reconciles: if pacman owns the tool, omarchy pkg drop it (graceful on dep-conflict refusal); if not on PATH, install via omarchy install dev-env. No path pinning — omarchy lands each tool wherever the underlying installer defaults today (Astral's ~/.local/bin/uv; mise's ~/.local/share/mise/shims/go) and command -v finds it. The user's rule: if a tool is installed in a way the repo doesn't declare, it should get replaced. Reconciling on ./install enforces that for the main drift vector (pacman) while staying robust to upstream path changes. Latest-at-bootstrap caveat: omarchy install dev-env pulls latest at the time it runs (mise @latest, Astral installer), so a fresh bootstrap on different days may yield different versions; make update runs uv self update; Quattro's main updater owns mise-backed tool and agent upgrades.
D-OPENCODE-LSP Global OpenCode LSP Keep Omarchy's seeded ~/.config/opencode/opencode.json, then use opencode/settings.jq to assert only "lsp": true. This enables every built-in server globally while preserving Omarchy defaults and unrelated user keys. Do not install a blanket system LSP bundle: OpenCode lazily starts matching servers and auto-installs many of them; runtimes and project-coupled servers remain with their projects or Omarchy's install dev-env path. OpenCode's current behavior is applicability-based, not a quality ranking: it starts all enabled servers whose extension, root-marker, and executable requirements match an opened file. A global setting applies from every launch directory, but cannot promise one objectively “best” server in every folder: project config may override global config, root discovery is bounded by the OpenCode instance/worktree, and missing SDKs or project dependencies can prevent a match. See F-OPENCODE-LSP.
D-PKG-REMOVE Baseline package/app curation Keep stock Quattro, then apply explicit deltas. packages.txt and packages.aur.txt add genuine extras; packages.remove.txt is the persistent deny-list applied with omarchy pkg drop. The broad Remove Preinstalled flow is not used because it also removes retained Quattro apps, OmaCalc, and agent wrappers.
  • packages.txt / packages.aur.txt — additive extras, processed through omarchy pkg add / omarchy pkg aur add. Coding agents and Obsidian are omitted because Quattro owns them. App channel choices follow the Omarchy-native audit in F-APP-CHANNELS: spotify uses Quattro's sync-repo service package, and slack-desktop is an intentional local AUR choice because Omarchy has no Slack package, webapp, binding, or migration. Operator CLI utilities use the same official-repository path: nmap comes from Arch extra through packages.txt. Security tooling follows F-MALWARE-SCANNER: clamav comes from Arch extra through packages.txt, while signature refreshes and scans remain explicit operator actions with no background daemon enabled.
  • packages.remove.txt — symmetric subtractive partner to packages.txt / packages.aur.txt, processed via omarchy pkg drop after both add steps so a name in both files resolves to "removed". Wrapped in warn-and-continue because pacman -Rns can refuse on reverse-dep conflicts. Empty list → no-op; already-absent names → no-op at the omarchy CLI layer. Scope: pacman-tracked only (official-repo + AUR). Web-app launcher curation is handled separately by D-WEBAPP.
  • Stale-launcher cleanup in install — explicit rm -f for known orphan ~/.local/share/applications/*.desktop files whose underlying package is gone but the user-dir launcher remained (pacman -Rns only removes files the package installed, not user-state files copied there later).
  • bin/.local/bin/pkg-residue — read-only audit for package leftovers after removal. It derives search terms from the package name and any known pacman/cache file list, uses rg --files as the fast path for file matches, uses find -type d for directory matches, filters paths owned by pacman, and reports likely residual user state, system state, and package cache entries without deleting anything.
A major upgrade can reinstall base packages and mark them explicit, so the deny-list is durable desired state rather than a one-time cleanup. install seeds a missing mutable OpenCode config only to apply the user's LSP delta; Quattro still owns the OpenCode binary through its mise wrapper. Audit rule: before adding a name to packages.remove.txt, grep /usr/share/omarchy/ for usage — Omarchy wires some "builtins" into keybindings or shell init (e.g. zoxide → cd alias, fzf → keybindings, btop → SUPER+CTRL+T). Removing one of those silently breaks omarchy commands, so clean up the matching wiring in our overlay in the same change (e.g. an hl.unbind in hypr/dotfiles.lua for a keybound tool — which is exactly why btop and eza are not dropped: btop is keybound and eza backs the ls alias).
D-WEBAPP Stock web-app curation Keep Quattro's native implementation and apply only an explicit launcher deny-list. webapps.remove.txt lists unwanted stock launchers; install processes each present entry through omarchy webapp remove. Discord and Zoom remain packaged and refreshed by Quattro, while the separately installed Tailscale launcher is retained because none appears in the deny-list. Either retained launcher is restored through omarchy refresh applications when missing, before removals are reapplied; lib/style.sh: RETAINED_WEBAPPS is the one list install and verify.sh share. verify.sh cmps each retained launcher against Quattro's packaged copy rather than restating its Exec= line. Quattro's broad Remove Preinstalled flow would also remove retained packages, OmaCalc, TUI wrappers, and mise-backed agent launchers. Its application refresh can recopy stock desktop files, so a small persistent delta is required. Calling the supported remover preserves Quattro's ownership of launcher and icon cleanup instead of restating or editing packaged files — which is also why the retained-launcher check compares against the packaged file instead of pinning an upstream URL.
D-BROWSER-DEFAULT Default browser Stable Brave Origin is the converged default browser. install calls omarchy install browser brave-origin only when the package is absent and omarchy default browser brave-origin only when the selected default differs. It verifies the resulting state, then asserts the additional HTML and scheme MIME handlers that xdg-settings does not cover. Quattro natively maps Brave Origin to stable, owns its flags, extensions, policies, and theme refresh. The repository hook and package/channel compatibility code are therefore deleted. The command's desktop notification can fail after state succeeds, so the following read-only default assertion is the safety gate.

Shell

Decision Choice Why
D-SHELL-BASH Login shell bash (Omarchy default). No chsh to zsh. Omarchy's boot/session/helpers assume bash; chsh→zsh is a documented footgun (F-SHELL-RESEARCH). Omarchy's bash already wires starship/zoxide/fzf/mise, so zsh's marginal gain is small.
D-SHELL-SEAM Aliases/functions Ported into ~/.config/dotfiles/shell.sh, sourced via the ~/.bashrc managed block (at EOF, so ours win). ~/.bashrc is owner-owned and "not overwritten on updates" (F-BASH-CHAIN). Aliases Omarchy already defines (t, g, gcm, gcam, n, cd/zoxide, ls/eza) are dropped in favor of Omarchy's.
D-SECRETS-LOCAL Secrets/host-specific Gitignored shell.local.sh holds personal and device-specific aliases, functions, and keybinds (Vertex project IDs, device serials, the Ctrl-F sessionizer bind, VPN/GCP helpers) — never install-path redirects, since Omarchy installs tools (uv, gcloud, …) natively on PATH. Keep the shared repo generic and secret-free.

D-CAPS-CTRL caps lock → control in (fragment) Moved off Omarchy's seeded input.conf into the owned fragment, sourced last.

D-LOOKNFEEL Looknfeel deltas in (fragment) An always-on "compact look" in the reloadable personal Lua module. (1) general { gaps_in = 2; gaps_out = 4 } — slim but present gaps (Omarchy's defaults are 5/10, Hyprland's own are 5/20). (2) general { border_size = 2 } — the one deliberate restatement of an Omarchy default in any overlay. This module loads after default.hypr.toggles, so window-no-gaps (which zeroes gaps, border and rounding) loses to every key stated here; omitting border_size would let that one through and leave the toggle half-applied — our gaps and rounding with no borders. See F-HYPR-SEAM. (3) decoration { rounding = 8 } — Hyprland defaults to 0; this is also the radius Omarchy applies to popups via o.window({ tag = "pop" }, { rounding = 8 }). (4) decoration { shadow, blur } — Quattro disables both, so enabled = true is the delta; only the sub-values that differ from Hyprland 0.56.2's own defaults are stated (shadow.range 2, blur.passes 2, blur.special, blur.brightness 0.72, blur.contrast 0.75), and the ones that matched it are deliberately absent. (5) a narrow terminal-class opacity rule at 0.86 0.78, without override — that keyword only stops the decoration:*_opacity globals multiplying in, and Quattro sets none of them.
D-MONITORS Known external monitor layouts in (fragment) Three monitor = lines in the overlay encode known external displays. The home dock layout is: DP-5 (Acer XV272U) primary at 0x0, DP-4 (Acer XV272U V) secondary at 1920x0, both at native 2560×1440 @ 144 Hz and compositor scale 1.333333 (effective logical 1920×1080 per panel — the secondary's position is in scaled pixels, hence 1920x0 rather than 2560x0; see F-MONITOR-SCALE-PERSIST for why we set scale in the overlay rather than via the Super + / cycle). The work monitor is DP-1 (Dell U2719DC) at 0x0, native 2560×1440 @ 59.95 Hz, compositor scale 1.25; its EDID advertises no higher-refresh native mode, so this rule favors the best-quality native resolution over lower resolution 75 Hz fallbacks. All are matched by full desc: identifier (description string up to but not including the trailing portname, per the Hyprland wiki — see F-MONITOR-RULE-APPLY) so cable-swaps between DP ports don't change the layout. The full serial tail is load-bearing because both Acer descriptions share the Acer Technologies XV272U prefix — a panel swap (same model, new EDID serial) silently falls through to the omarchy wildcard, so update the desc: string when that happens. No hot-plug script: Hyprland re-applies monitor = rules on every monitor connect, which is the same matcher behavior that makes omarchy's seeded fallback monitor=,preferred,auto,auto work; the omarchy-shipped omarchy-hyprland-monitor-watch already covers removal recovery. No workspace = N, monitor:… pins — on a fresh session, Hyprland assigns workspace 1 to the leftmost monitor by position (DP-5 at 0x0), which is what "primary" means here (Hyprland has no xrandr-style primary concept). One nuance: when these rules first land via hyprctl reload on a running session, the existing workspace→monitor bindings are preserved — workspace 1 stays on whichever monitor it was on, and fully migrates only on next fresh login (or move it now with hyprctl dispatch movecurrentworkspacetomonitor DP-5). eDP-1 is deliberately not in the overlay: omarchy's lid-switch handler at default/hypr/bindings/utilities.conf calls omarchy-hyprland-monitor-internal off/on, which writes monitor=eDP-1,disable to ~/.local/state/omarchy/toggles/hypr/internal-monitor-disable.conf. Our overlay loads after the toggles (F-HYPR-SEAM), so an explicit eDP-1 rule here would silently beat the toggle. The wildcard monitor=,preferred,auto,auto already activates eDP-1 at its only supported mode (1920×1200 @ 120 Hz) when the toggle isn't present. Same load-order pattern as D-LOOKNFEEL but inverted: silence to let the downstream toggle win, instead of re-stating to beat it. GDK_SCALE intentionally untouched: Quattro seeds hl.env("GDK_SCALE", …) from a local omarchy_gdk_scale in monitors.lua (stock 2, right for the laptop's 13"/2.8K panel), which omarchy-hyprland-monitor-scaling rewrites alongside the monitor scale. GDK_SCALE is process-global on Wayland — there is no per-monitor GTK scaling without per-app launchers — so dropping it to 1 for the 1440p externals would shrink GTK apps on eDP-1. The compositor scale in our hl.monitor entries are the in-scope correctness step; the GTK-oversize trade on the externals is acceptable until per-app launchers become worth it. Forward risk: when omarchy ships the Lua hyprland config (F-LUA), these lines become hl.monitor({…}) calls; the design is unaffected.
D-KINESIS-REMAP Kinesis Adv360 SmartSet thumb remap done Profile-1 thumb cluster reworked for Omarchy's SUPER-centric binds: SUPER on both bottom thumb keys ([end]>[lwin], [pgdn]>[rwin]) for either-hand chording; Alt moved to the freed inner-right key ([rwin]>[ralt]); Home→Tab ([home]>[tab]) so SUPER/ALT+Tab are thumb gestures; and Calc→F14 ([pgup]>[f14]) bound by keycode (code:192, since F13+ keysyms map unreliably through xkb) to the clipboard manager. Caps left as-is; Delete stays on the fn layer. Layout backed up at kinesis/layout1.txt.

Quickshell deltas

The overlay carries one supported Quickshell plugin for dynamic workspaces, placed with Quattro's own omarchy bar CLI. Both shell.toml and shell.json stay mutable and user-owned; the repo writes nothing into shell.toml, so bar colors follow the active theme.

Decision Choice Why
D-QUICKSHELL-DELTAS Quickshell overlay shape Stow the supported user-owned pashbyl.workspaces plugin. Keep shell.toml mutable and set nothing in it: pinning bar.active would override every theme's red with Quickshell's own #a55555 fallback. Keep shell.json mutable and converge module IDs and ordering with Quattro's own omarchy bar / omarchy plugin CLI, which sources the same omarchy-shell-config normalize/commit helpers a hand-written jq filter used to reimplement. plugin disable clears the stock workspaces module, which an Omarchy update can re-place, and bar put places the personal clone after the menu without moving an already-placed one, so upstream re-additions and interrupted runs converge to the same state. Quattro documents plugins as the supported widget seam, and its own omarchy bar CLI already owns layout convergence, so the repo drives that rather than reimplementing it. Quickshell atomically replaces shell.toml when settings change, which is why it stays unstowed and unwritten.

Terminal (Ghostty default)

Decision Choice Why
D-TERM-GHOSTTY Ghostty is the default terminal; Alacritty removed install installs Ghostty only when its package is absent, selects it with omarchy default terminal only when the default differs, and adds alacritty and foot to packages.remove.txt. The omarchy CLI is the whole mechanism: it installs the package, seeds ~/.config/ghostty when missing, and rewrites ~/.config/xdg-terminals.list — whose first entry is the sole definition of the default terminal (Super+Return goes through xdg-terminal-exec). The install step runs before the package drop so the list never points at an already-removed terminal. Separate package and default guards make re-runs idempotent while still repairing either half of the state independently. The commands' notification tails are fail-open; a following read-only default assertion is the safety gate. After the package drop, install also removes Omarchy migration 1763558828's user-owned ~/.local/share/applications/Alacritty.desktop when it exists. Quattro's application refresh also copies foot.desktop independently of the package, so install removes that user-level launcher too. Both live in lib/style.sh: STALE_TERMINAL_LAUNCHERS as package:launcher pairs, so install removes and verify.sh asserts under the same package-absent guard — a launcher is legitimate while its terminal is still installed. Pacman does not own or remove these user files. No terminal config is carried — Omarchy seeds ghostty, and ghostty's default right-click is a context menu (not paste), so the former Alacritty right-click no-op overlay was retired rather than ported. Letting the omarchy CLI own the desktop-entry id and the list is the delta-only, omarchy-native path (D-DELTA-STORAGE); hand-writing xdg-terminals.list would pin an omarchy-owned detail (com.mitchellh.ghostty.desktop). Removal uses the existing D-PKG-REMOVE mechanism because leaving an explicitly-unwanted package installed isn't "respecting defaults". The pre-removal audit confirmed Alacritty is safe to drop: Required By: None, omarchy-launch-screensaver dispatches on the actual default terminal (it has a ghostty branch), and every other omarchy script naming alacritty.toml is guarded by an [[ -f ]] test so it no-ops when the file is gone. The one durability caveat: a manual package-reinstall recovery flow (never omarchy update) reinstalls base packages including alternate terminals; package and stale-launcher cleanup are idempotent, so re-running ./install re-drops both. make verify checks the default, packages, and user launchers so this residue cannot pass unnoticed again.

Prompt (Starship) deltas

Decision Choice Why
D-STARSHIP-VENV Show the active Python venv name in the prompt starship's built-in python module prints just the active venv's name (e.g. (.venv)) — and nothing when no venv is active, in any directory. Emptying every detect_* list leaves detect_env_vars (which already defaults to ["VIRTUAL_ENV"]) as the module's only trigger, so it is directory-independent; omitting $version from its format is what keeps it from exec'ing python, making the indicator fork-free. Omarchy seeds a stripped format, which install splices $python into before $character; right_format is not used because starship's bash init only renders it under ble.sh, so a reference parked there would be invisible. The module table rides a standard upsert_block managed block, styled italic yellow. One behaviour change from the retired custom module: $virtualenv prefers the prompt field in the venv's pyvenv.cfg and only falls back to the directory basename, where the old basename call always showed the directory name. verify.sh greps the $python reference, fails on an unrenderable right_format, and check_blocks the module. A $VIRTUAL_ENV-keyed custom module, not starship's native python module. The python module is starship's default venv display, but it only renders inside a detected Python-project directory and bundles via 🐍 <version>; the goal here is just the venv name, shown whenever a venv is active regardless of directory — exactly what a custom module on $VIRTUAL_ENV expresses. Storage is a hybrid in-place delta: the format reference must edit Omarchy's scalar format key — starship has no include and TOML can't merge two formats. D-QUICKSHELL-DELTAS sidesteps that wall with structured jq, but a format reference has no append or merge option, so this is a deliberate text-level sed — the repo's one in-place text edit. The module table, by contrast, is append-only and rides the standard managed block. Not stowed: ~/.config/starship.toml is seeded once (an Omarchy migration cps the default only if omarchy-cmd-missing starship), is never auto-refreshed, and only the manual omarchy refresh config starship.toml rewrites it — its cp -f would write through a stow symlink (F-REFRESH-WRITETHROUGH), and owning the whole file would restate and freeze Omarchy's seeded defaults, against the deltas-only rule (D-DELTA-STORAGE).

Claude Code config

Decision Choice Why
D-CLAUDE-CONFIG Track Claude Code's custom config Consolidate the two genuine custom-config artifacts under ~/.claude, split by how Claude Code treats them. statusline-command.sh (a self-contained prompt script Claude never rewrites, coloured with plain ANSI so the terminal renders it in the active Omarchy theme) is stowed via a new claude package, like tmux/local.conf. Claude Code itself is themed the same Omarchy-native way as foot and tmux: omarchy-theme-set regenerates ~/.claude/themes/omarchy.json on every theme change via omarchy-theme-set-claude, and the overlay opts in with .theme = "custom:omarchy". install seeds the file by calling that same helper without --activate (which would write .theme itself and fight the jq delta). Because the helper exits 0 without writing anything when the theme state was never generated, install warns and verify.sh checks for the theme file — a pinned .theme with no theme file is a dangling reference. settings.json is instead applied as an idempotent jq delta (claude/settings.jq + apply_jq_deltas) that install overlays onto the live file, seeding {} first so a pre-first-run box still converges. Because that filter is a build input read in place — not a dotfile — a claude/.stow-local-ignore keeps stow from symlinking it into $HOME (it sits at the package root, so it would otherwise land at ~/settings.jq). The default model and effort level are pinned as .env.ANTHROPIC_MODEL = "opus" and .env.CLAUDE_CODE_EFFORT_LEVEL = "xhigh" in the same overlay — not the top-level model / effortLevel keys: the /model and /effort pickers own and rewrite those keys (selecting Default even clears model), so a pinned key drifts on every switch, but neither picker touches .env, so the overlay stays a no-op. Claude Code applies its settings env block to the session (verified: it selects the model; CLAUDE_CODE_EFFORT_LEVEL is read from the env and is session-only), so these set the startup defaults while /model and /effort still switch at runtime. verify.sh link-checks the script and confirms the settings overlay landed (which covers the env pin). Tool-rewritten JSON gets a delta, not a symlink. Claude Code rewrites settings.json itself (via /config), so stowing it risks the same write-through / rename-detach failure that keeps Omarchy-owned files off symlinks (F-REFRESH-WRITETHROUGH); asserting only our keys via jq preserves anything Claude adds and re-converges every run — the same trade as D-QUICKSHELL-DELTAS. The repo therefore never contains settings.json, only the filter, so no credential or machine state can leak. Everything else under ~/.claude is secrets/state/cache (.credentials.json, ~/.claude.json, projects/ transcripts + auto memory, history, caches, sessions) and is deliberately excluded — nothing there is tracked.

Baseline & bindings.conf D-BASELINE

Reference baseline = stock Quattro plus explicit deltas Do not run the broad Remove Preinstalled flow: it also removes retained Quattro apps, OmaCalc, and lazy agent wrappers. Start from stock Quattro, apply additive manifests and the narrow package deny-list, and leave Omarchy-owned bindings untouched except for explicit personal Lua overrides. Reproduction recipe: install Quattro → ./install.
