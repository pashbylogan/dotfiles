Research Findings

How Omarchy actually behaves

Verified by reading the live system (omarchy 3.8.2) and Omarchy's source/manual. These facts justify the architecture. Each finding has a stable ID (see Trace).

Hyprland config is a sourcing seam F-HYPR-SEAM

~/.config/hypr/hyprland.conf is a seeded, owner-owned file that sources, in order:

  1. Omarchy defaults in ~/.local/share/omarchy/default/hypr/* — never edit these;
  2. the user override files: monitors.conf, input.conf, bindings.conf, looknfeel.conf, autostart.conf;
  3. ~/.config/omarchy/current/theme/hyprland.conf;
  4. ~/.local/state/omarchy/toggles/hypr/*.conf.

Later sources win. Our fragment is added after all of these (managed block at EOF of hyprland.conf), so it overrides cleanly.

Refresh / reset writes can mutate tracked files F-REFRESH-WRITETHROUGH

  • omarchy-refresh-config does create timestamped backups before overwriting.
  • But it copies defaults with cp -f — if the destination is a symlink into git, the copy writes through the symlink and mutates the tracked source. This is the real reason we never symlink Omarchy-owned files.
  • omarchy refresh hyprland resets the whole set of hypr user files at once — so a single added source = line is the smallest, most recoverable integration surface.

Hyprland is migrating to Lua (already on dev) F-LUA

Forward risk Omarchy's dev-branch omarchy-refresh-hyprland refreshes hyprland.lua, bindings.lua, input.lua, looknfeel.lua, monitors.lua, autostart.lua, .luarc.json. The installed system is still .conf, but the transition is real and close. A large .conf-capturing layer would have a looming expiry — which is why this repo owns only a small fragment + one integration line.

The bash chain F-BASH-CHAIN

Login flow: /etc/profile → ~/.bash_profile → ~/.bashrc → ~/.local/share/omarchy/default/bash/rc. The default bash already wires starship, zoxide, fzf, mise, eza/bat aliases, completions, and a functions library. The owner-owned ~/.bashrc sources the Omarchy default and leaves a user section at EOF — so our managed block lands there and wins conflicts.

Aliases/functions Omarchy already defines (so we defer to them, or override only intentionally): ls/lt (eza), cd/zd (zoxide), t (tmux), g/gcm/gcam/gcad, n() (nvim), ga/gd (worktrees), tdl/tdlm/tsl (tmux layouts), fip/dip/lip (ssh forwarding), transcoding helpers.

The manual confirms: ~/.bashrc "will not be overwritten on updates" — the safe seam for shell customization.

Neovim is fully Omarchy-owned F-NVIM-OWNED

omarchy-nvim-setup does cp -r .../config ~/.config/nvim — it replaces the entire nvim tree (backing up first via mv, behind a gum confirm). The file ~/.config/nvim/lua/config/keymaps.lua already exists as the LazyVim user-extension point ("Add any additional keymaps here"). Therefore we do not stow into ~/.config/nvim; instead install upserts a managed block into that keymaps.lua. It survives routine omarchy update (only the deliberate, confirm-gated setup re-copies nvim); re-run ./install after such a reset.

Baseline: "Omarchy after Remove Preinstalled" F-BASELINE

The owner's first post-install step was Remove Preinstalled (omarchy menu), which removed bundled apps (Spotify, Obsidian, Signal, Typora, 1Password, lazydocker, the webapps, …). That is why the live ~/.config/hypr/bindings.conf lacks their launcher bindings, whereas vanilla Omarchy ships ~20 of them. This divergence is intentional. The repo's reference baseline is the post-Remove-Preinstalled state, and bindings.conf is left Omarchy-owned and untracked.

Omarchy CLI surface (idempotent, preferred over re-implementing) F-CLI

CommandDoes
omarchy pkg add <pkgs>pacman -S --needed; no-op if present. omarchy pkg aur add for AUR (yay).
omarchy pkg drop <pkgs>pacman -Rns, installed-only.
omarchy refresh config <path>reset one ~/.config file to default (backs up).
omarchy theme/font <...>theme/font management (set only if different).
omarchy update -yfull update: pulls Omarchy, pacman -Syu, migrations, AUR. Skips the initial confirm/menu — but may still prompt (gum) for required restart/reboot handling.

Shell research (zsh vs. bash) F-SHELL-RESEARCH

Keeping zsh would buy mainly inline autosuggestions + syntax highlighting + zsh completion/globbing — narrow, since Omarchy's bash already provides starship/zoxide/fzf/mise. Against that, chsh→zsh breaks Omarchy's bash-dependent boot/session/helpers (env not loaded in the Hyprland session; reported black-screen cases). Conclusion: stay on bash; layer aliases via the ~/.bashrc seam.

tmux prefers ~/.config/tmux/tmux.conf over ~/.tmux.conf F-TMUX-XDG

Omarchy ships a full ~/.config/tmux/tmux.conf (themed status bar, tmux-256color + *:RGB truecolor, mouse on, 50k history, set-clipboard, extended-keys, M-<n>/M-arrow window nav, C-M-arrow pane nav). tmux loads the XDG path in preference to ~/.tmux.conf, so a stowed ~/.tmux.conf is silently shadowed and never read. We therefore stow our config to ~/.config/tmux/local.conf and source-file it LAST from omarchy's tmux.conf (managed block) — overriding only our intentional deltas (C-a prefix, vi-copy→wl-copy, hjkl nav, sessionizer) while inheriting omarchy's good defaults. Related: omarchy fixes ssh flakiness via MTU probing (install/config/ssh-flakiness.sh), not TERM, so a global TERM=xterm-256color ssh alias is unnecessary and was removed.
