Research Findings

How Omarchy actually behaves

Verified by reading the live system (omarchy 3.8.2), Omarchy's source/manual, and selected agent-tool documentation. These facts justify the architecture. Each finding has a stable ID (see Trace).

Hyprland config is a sourcing seam F-HYPR-SEAM

~/.config/hypr/hyprland.conf is a seeded, owner-owned file that sources, in order (verified against the live machine and omarchy's shipped seed at ~/.local/share/omarchy/config/hypr/hyprland.conf):

  1. Omarchy defaults in ~/.local/share/omarchy/default/hypr/* — never edit these;
  2. the active theme: ~/.config/omarchy/current/theme/hyprland.conf;
  3. the user override files: monitors.conf, input.conf, bindings.conf, looknfeel.conf, autostart.conf;
  4. ~/.local/state/omarchy/toggles/hypr/*.conf.

Later sources win. Our fragment is added after all of these (managed block at EOF of hyprland.conf), so it overrides cleanly. The toggles-before-fragment ordering is the load-order trap behind two opposite-direction deltas: in D-LOOKNFEEL we re-state border_size = 2 in the fragment to beat the window-no-gaps toggle, while in D-MONITORS we deliberately stay silent on eDP-1 so the internal-monitor-disable.conf toggle retains control.

Refresh / reset writes can mutate tracked files F-REFRESH-WRITETHROUGH

  • omarchy-refresh-config does create timestamped backups before overwriting.
  • But it copies defaults with cp -f — if the destination is a symlink into git, the copy writes through the symlink and mutates the tracked source. This is the real reason we never symlink Omarchy-owned files.
  • omarchy refresh hyprland resets the whole set of hypr user files at once — so a single added source = line is the smallest, most recoverable integration surface.

Hyprland is migrating to Lua (already on dev) F-LUA

Forward risk Omarchy's dev-branch omarchy-refresh-hyprland refreshes hyprland.lua, bindings.lua, input.lua, looknfeel.lua, monitors.lua, autostart.lua, .luarc.json. The installed system is still .conf, but the transition is real and close. A large .conf-capturing layer would have a looming expiry — which is why this repo owns only a small fragment + one integration line.

The bash chain F-BASH-CHAIN

Login flow: /etc/profile → ~/.bash_profile → ~/.bashrc → ~/.local/share/omarchy/default/bash/rc. The default bash already wires starship, zoxide, fzf, mise, eza/bat aliases, completions, and a functions library. The owner-owned ~/.bashrc sources the Omarchy default and leaves a user section at EOF — so our managed block lands there and wins conflicts.

Aliases/functions Omarchy already defines (so we defer to them, or override only intentionally): ls/lt (eza), cd/zd (zoxide), t (tmux), g/gcm/gcam/gcad, n() (nvim), ga/gd (worktrees), tdl/tdlm/tsl (tmux layouts), fip/dip/lip (ssh forwarding), transcoding helpers.

The manual confirms: ~/.bashrc "will not be overwritten on updates" — the safe seam for shell customization.

Neovim is fully Omarchy-owned F-NVIM-OWNED

omarchy-nvim-setup does cp -r .../config ~/.config/nvim — it replaces the entire nvim tree (backing up first via mv, behind a gum confirm). The file ~/.config/nvim/lua/config/keymaps.lua already exists as the LazyVim user-extension point ("Add any additional keymaps here"). Therefore we do not stow into ~/.config/nvim; instead install upserts a managed block into that keymaps.lua. It survives routine omarchy update (only the deliberate, confirm-gated setup re-copies nvim); re-run ./install after such a reset.

Baseline: "Omarchy after Remove Preinstalled" F-BASELINE

The owner's first post-install step was Remove Preinstalled (omarchy menu), which removed bundled apps (Spotify, Obsidian, Signal, Typora, 1Password, lazydocker, the webapps, …). That is why the live ~/.config/hypr/bindings.conf lacks their launcher bindings, whereas vanilla Omarchy ships ~20 of them. This divergence is intentional. The repo's reference baseline is the post-Remove-Preinstalled state, and bindings.conf is left Omarchy-owned and untracked.

App channels: Omarchy-native first F-APP-CHANNELS

App curation starts with Omarchy's own code and docs, then checks upstream app support and Arch packaging. On this machine that yields four current channel outcomes: brave-origin uses a temporary stable-channel compatibility overlay (D-BROWSER-DEFAULT) because Omarchy's current native browser installer/default path still targets brave-origin-beta-bin while Brave documents, and the AUR exposes, stable brave-origin-bin. The overlay still reuses Omarchy's package, flags, policy, theming, and hook surfaces; spotify stays on the AUR package because Omarchy lists spotify in omarchy-base.packages and binds Music to omarchy-launch-or-focus spotify; obsidian stays in Arch extra because Omarchy lists obsidian, migrated obsidian-bin to obsidian, moved its launch flags into ~/.config/obsidian/user-flags.conf, and themes Obsidian vaults; slack-desktop stays as a local AUR choice because Omarchy has no Slack package, webapp, binding, or migration.

The Slack exception is deliberately narrow. Native Slack provides the installed app identity and slack:// handler, and the local tray already works without adding libappindicator. Slack's Linux docs call the desktop app beta, support Ubuntu/RHEL directly, and list huddles on desktop plus Google Chrome on Linux. So the durable baseline is native slack-desktop, with Slack in Google Chrome as the huddles/screen-share fallback if the native app regresses. Do not install or remove anything for these three apps unless that local behavior changes.

Omarchy CLI surface (idempotent, preferred over re-implementing) F-CLI

Command Does
omarchy pkg add <pkgs> pacman -S --needed; no-op if present. omarchy pkg aur add for AUR (yay).
omarchy pkg drop <pkgs> pacman -Rns, installed-only. Drives D-PKG-REMOVE's declarative packages.remove.txt surface.
omarchy refresh config <path> reset one ~/.config file to default (backs up when a destination exists; otherwise seeds the missing file).
omarchy theme/font <...> theme/font management (set only if different).
omarchy update -y full update: pulls Omarchy, pacman -Syu, migrations, AUR. Skips the initial confirm/menu — but may still prompt (gum) for required restart/reboot handling.
omarchy update firmware firmware via fwupdmgr refresh --force + sudo fwupdmgr update. Separate invocation — not chained from omarchy update -y.
omarchy install dev-env <kind> Canonical install path for language tools. Today python installs Python via mise use --global python@latest then drops uv via Astral's installer; go uses mise use --global go@latest. Pulls latest at the moment it runs (no version pin) — see D-DEV-ENV.
omarchy install browser <kind> Canonical install path for supported browsers. For brave-origin, current Omarchy installs brave-origin-beta-bin. Until upstream PR #6021 or equivalent ships, this repo mirrors the script's policy/flags steps against stable brave-origin-bin instead of calling the wrapper.
omarchy default browser <kind> Sets XDG's default web browser and the http/https/text/html MIME handlers. Current Omarchy still maps brave-origin to brave-origin-beta.desktop, so this repo sets the stable brave-origin.desktop handlers directly until the upstream mapping changes.

Shell research (zsh vs. bash) F-SHELL-RESEARCH

Keeping zsh would buy mainly inline autosuggestions + syntax highlighting + zsh completion/globbing — narrow, since Omarchy's bash already provides starship/zoxide/fzf/mise. Against that, chsh→zsh breaks Omarchy's bash-dependent boot/session/helpers (env not loaded in the Hyprland session; reported black-screen cases). Conclusion: stay on bash; layer aliases via the ~/.bashrc seam.

tmux prefers ~/.config/tmux/tmux.conf over ~/.tmux.conf F-TMUX-XDG

Omarchy ships a full ~/.config/tmux/tmux.conf (themed status bar, tmux-256color + *:RGB truecolor, mouse on, 50k history, set-clipboard, extended-keys, M-<n>/M-arrow window nav, C-M-arrow pane nav). tmux loads the XDG path in preference to ~/.tmux.conf, so a stowed ~/.tmux.conf is silently shadowed and never read. We therefore stow our config to ~/.config/tmux/local.conf and source-file it LAST from omarchy's tmux.conf (managed block) — overriding only our intentional deltas (C-a prefix, vi-copy→wl-copy, hjkl nav, sessionizer) while inheriting omarchy's good defaults. Related: omarchy fixes ssh flakiness via MTU probing (install/config/ssh-flakiness.sh), not TERM, so a global TERM=xterm-256color ssh alias is unnecessary and was removed.

Waybar config drifts via two omarchy patterns F-WAYBAR-MIGRATIONS

The omarchy Dotfiles page claims files in ~/.config "will not be overwritten on updates" — but the Common tweaks page quietly admits "it might occasionally be necessary for system updates to restore certain configs to their original condition" and instructs the user to find their old version in a .bak file. For waybar the second claim is the accurate one: ~/.config/waybar/config.jsonc is mutated by omarchy updates two distinct ways.

  1. Wholesale overwrite via omarchy-refresh-waybar (a thin wrapper around omarchy-refresh-config waybar/config.jsonc), which backs up the user file as config.jsonc.bak.<epoch> and then cp -fs the upstream default over it. Invoked from migrations such as 1751887718.sh, 1752725616.sh, and 1753495989.sh.
  2. Surgical sed -i edits against the live user file, guarded by grep idempotency checks. Examples: 1763409505.sh inserts "10": "0"; 1764067068.sh adds the bluetooth-off icon; 1771602647.sh injects the notification-silencing indicator.

These coexist on purpose: refresh-waybar handles structural changes; surgical migrations add single keys without disturbing personal edits to the rest of the file. The implication for this repo is that forking the whole config.jsonc would silently drop every future surgical migration (we'd never see the new keys upstream adds), while leaving the file unmanaged means a periodic refresh-waybar erases personal edits. The resolution lives in D-WAYBAR-DELTAS: own only the deltas as jq filters, applied idempotently on every ./install.

Agent instruction files should be concise and concrete F-AGENT-GUIDANCE

AGENTS.md is the most universal repo-root name for shared coding-agent guidance: the AGENTS.md project describes it as a predictable "README for agents" and lists common sections such as setup, testing, code style, and security. Claude Code now documents AGENTS.md interoperability explicitly: Claude itself reads CLAUDE.md, but a project can make Claude consume the shared guidance by importing @AGENTS.md from CLAUDE.md. Aider similarly recommends putting coding conventions in a small markdown file and loading it read-only.

The writing guidance is consistent across current toolchains: keep the file lean because it consumes model context, use specific/verifiable instructions instead of vague "best practices", put exact commands near the top, and treat the file as advisory guidance rather than a hard policy layer. This repo's AGENTS.md therefore records only frequently relevant commands, boundaries, traceability rules, and the comment conventions; durable explanations and source-backed rationale stay in docs/.

Harness coverage. As of May 2026, AGENTS.md at repo root is read natively by Codex, opencode, crush, Cursor, GitHub Copilot's coding agent, Windsurf, Cline, Continue.dev, JetBrains Junie, Sourcegraph Amp, Devin, Kilo Code, and Zed (with caveats). The only harness in our mix that does NOT yet auto-load AGENTS.md is Claude Code (tracked in anthropics/claude-code#34235). Bridge: a one-line CLAUDE.md containing @AGENTS.md — Claude Code's @file import pulls the canonical file into every session, and Anthropic's auto-memory writes land in the small bridge file rather than mutating AGENTS.md. The bridge is enforced by .github/scripts/check_docs.py check #11, which also guards the 32 KiB Codex cap on AGENTS.md content.

What we deliberately don't add. Legacy harness-specific files (.rules, .cursorrules, .windsurfrules, .clinerules, .github/copilot-instructions.md, AGENT.md) are not created at repo root: Zed's "first-match wins" precedence ranks several of these above AGENTS.md and would shadow it, opencode reads only the first matching file per category, and most harnesses that read both end up loading duplicated content. The canonical-plus-bridge pattern keeps the root clean and the source of truth singular.

Hyprland monitor = rules re-apply on hot-plug; desc: is a prefix match; empty-output is a fallback F-MONITOR-RULE-APPLY

Three facts from the Hyprland monitors documentation constrain D-MONITORS:

  • desc: matches a prefix of the description. The wiki: "the description value up to, but not including the portname can be used as the output field with a desc: prefix." When two connected monitors share a prefix (the two Acer XV272U variants on this dock do), the rule must extend the prefix until it's unique. The repo uses the full description string (including the EDID-reported serial tail) in both the overlay and the docs, so the rule reads as "this exact unit" rather than relying on a shortest accident.
  • Empty-output rules are fallback-only. Wiki: "Leaving the output empty will define a fallback rule to use when no other rules match." So omarchy's seeded monitor=,preferred,auto,auto in ~/.config/hypr/monitors.conf is outranked by every specific desc: or name-matched rule — no need to edit monitors.conf to add specific rules.
  • The matcher fires on hot-plug, not only at startup. The "quickly plugging in random monitors" recommendation in the wiki is precisely a hot-plug pattern — the fallback rule is described as applying "when not specified", which by the same mechanism makes any specific monitor = rule auto-apply when a matching monitor is later connected. That delivers the D-MONITORS requirement of "reloaded every time the laptop is plugged into these displays" with zero script: omarchy's omarchy-hyprland-monitor-watch handles the removal-recovery half; Hyprland's built-in matcher handles the connect half.

Both the current Hyprland wiki and the archived 0.54 wiki page agree on these semantics — see the Sources list. The current page renders Lua examples (Hyprland is migrating to Lua, see F-LUA); the 0.54 page is closer to the .conf/hyprlang dialect omarchy 3.x still ships, but the matcher contract is identical.

Omarchy's Super + / scale cycle auto-persists only the single-wildcard monitors.conf shape F-MONITOR-SCALE-PERSIST

The omarchy manual recommends editing ~/.config/hypr/monitors.conf to set persistent monitor scale, and the runtime cycle keybind Super + / (script omarchy-hyprland-monitor-scaling-cycle) walks 1 → 1.25 → 1.6 → 2 → 3 → 4 via hyprctl keyword monitor …. The script also writes the new scale through to monitors.conf so it survives reboot — but only when monitors.conf contains exactly one monitor= line and that line matches the regex ^monitor=,preferred,auto, (the omarchy-seeded wildcard).

For a multi-monitor layout matched by desc: rules — as D-MONITORS uses — the auto-persist branch is skipped, so the runtime Super + / change reverts at the next reload. The omarchy-native persistence path in that case is the same one the rest of this repo already uses: own the monitor = deltas in our last-sourced overlay (F-HYPR-SEAM), which also stays safe from omarchy refresh hyprland (F-REFRESH-WRITETHROUGH). The wiki tool hyprmon helps with positioning but has the same persistence gap, and third-party hyprdynamicmonitors would fill it but is not bundled.

Omarchy ships ssh-agent dormant F-SSH-AGENT

OpenSSH installs ssh-agent.socket as a systemd user unit at /usr/lib/systemd/user/ssh-agent.socket, but the unit ships disabled and Omarchy's shell init never exports SSH_AUTH_SOCK. A fresh box that runs ssh-add therefore gets "Could not open a connection to your authentication agent." GUI apps launched through uwsm-app have the same problem unless the socket is published through UWSM's environment loading path; otherwise Obsidian Git operations fall back to repeated askpass prompts. Two one-time costs make the socket usable for the Omarchy desktop session: a per-machine systemctl --user enable --now ssh-agent.socket (manual per D-SCRIPTS-MINIMAL) plus a guarded SSH_AUTH_SOCK export in the stowed ~/.config/uwsm/env.d/dotfiles.sh fragment. UWSM reads that fragment when the graphical session starts, so Obsidian and Omarchy-launched terminals pick it up on the next Omarchy login.

Socket activation means the agent process is lazy-spawned on first connection to the socket, not at boot — so a fresh session starts with no keys cached, and they stay uncached across reboots unless something re-adds them. The matching ~/.ssh/config delta (AddKeysToAgent yes under Host *) reduces this to one passphrase prompt per session without pulling in gnome-keyring, keychain, or pam_ssh. Omarchy's official docs are silent on SSH key management, so this is an upstream-Arch convention bolted on as a small delta rather than an Omarchy-blessed flow.

The uwsm export is guarded — it only fires when SSH_AUTH_SOCK is unset and XDG_RUNTIME_DIR is set. The first guard preserves a pre-existing agent path (forwarded ssh -A sockets, 1Password's ~/.1password/agent.sock, gcr-ssh-agent.socket publishing $XDG_RUNTIME_DIR/gcr/ssh, gpg-agent with SSH emulation) instead of silently overriding it; the second makes the fragment inert if UWSM ever evaluates it before the runtime directory is available.
