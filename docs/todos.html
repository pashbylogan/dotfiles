waybar Personal waybar deltas split across two coupled overlays: jq filters in waybar/deltas.jq for config.jsonc (applied by install's apply_jq_deltas helper) and a managed block in style.css (via the existing upsert_block helper) for the matching CSS. waybar restarts only when content actually changed (hash-compare around both files) and the restart polls pgrep -x waybar to verify the process came back. New decision / finding pair documents the pattern and the omarchy mutation surface that makes a delta overlay safer than either a fork or a direct edit: D-WAYBAR-DELTAS, F-WAYBAR-MIGRATIONS. Initial deltas: drop the 1-5 persistent-workspaces pin so workspaces grow i3-style; add an icon-only memory module (glyph  nf-fa-bars, after cpu, on a 5 s interval) with used/total/% in tooltip-format on hover; extend omarchy's #cpu, #battery, ... CSS selector to include #memory so the new module renders with matching margins. The jq filter is defensive: refuses non-object roots, merges the memory module instead of replacing it, and checks all modules-* groups before inserting so a future omarchy reshuffle can't produce duplicates. Battery-audited: zero added wake events at the design level (verbose 1 s clock tick considered and deliberately rejected because it would prevent deep C-states). done

future Toggle-conditional compact look If the compact look should switch off, not just always apply Today the D-LOOKNFEEL compact deltas (slim gaps, border_size = 2, rounding = 8) are always on: the overlay sources last and overrides omarchy's window-no-gaps toggle, so SUPER+SHIFT+BACKSPACE and the menu "Gaps" entry are no-ops. To make the toggle flip between pure omarchy default (off) and compact (on), we must own the trigger: omarchy rewrites the toggle's state file from a read-only template (default/hypr/toggles/window-no-gaps.conf) on every enable, so editing that file isn't durable, and an always-on overlay can't tell which state it's in. future Folder icon variants (gray-body / colored-fold aesthetic) If revisiting Nautilus theming Investigated 2026-05-30 and backed out — keeping the trade-off study so future-me doesn't re-tread:
  • The "gray body, accent in the fold" look is the 2020-era Yaru design (Ubuntu 20.04 era). Upstream Yaru dropped it in ~22.04; modern Yaru and every bundled accent variant on omarchy ships fully-tinted folder bodies. Yaru-*-dark siblings only adjust status-bar glyphs for dark backgrounds — folder PNGs are near-identical to the light siblings.
  • The design survives in the Jannomag/Yaru-Colors fork (AUR yaru-colors-icon-theme; upstream unmaintained). But the fork only ships places/ (folder) icons — verified 0 app icons across the whole tree. Its Inherits=Yaru,Humanity,hicolor chain means GTK app-icon lookups fall through to plain Yaru's orange palette.
  • Net effect of installing the fork + flipping gsettings: Nautilus shows gray-body folders ✓, walker shows orange app icons (Yaru fallback). The Nautilus/walker mismatch was the reason this got reverted.
  • Mismatch is structural to the fork's design. Three landable paths if revisited: (a) accept gray-folders + orange-apps; (b) pivot to Papirus/Tela/Reversal — full app sets but fully-tinted folder bodies (different aesthetic); (c) author a custom merged theme (Yaru-Colors folders + Papirus apps), fragile across package updates.
  • Effort: high. Re-opening this without a clean aesthetic spec just churns. Likely best to wait for an upstream icon theme that ships gray-body folders and a coherent app set.
